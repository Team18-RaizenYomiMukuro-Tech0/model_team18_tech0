# 共有リンクが約 60 秒止まった件の見立てと対策案（2026-11-25）

origin: internal ／ 根拠: PR #704（`evidence/share-outage-study/README.md`・`load.mjs`。Terao の調査。マージ済み c3ceb7d）

**原因は確定していない。** 以下の「原因」は、手元の再現とコードからの見立て。Azure 上の実測は、PM の確認待ち。

## 1. 起きたこと（事実）

- 11/24 の発表中、共有リンクを開いたとき、画面側が約 60 秒応答しなかった（調査 README §4 の「60 秒の無応答と 503」）。
- PM の決定（11/25「原因を調べて案にする」）で調査した。アプリのコードも、本番も触っていない。

## 2. 見立て（意見。Azure の実測が無い）

- **（主）画面側の CPU が足りなくなった。** 画面側は 1 台（B1・1 vCPU）。共有ページの 1 訪問は、HTML 1 本と JS 9・CSS 2・画像 3 の計 15 リクエストで、手元の CPU は約 39 ms。大半は HTML の描画ではなく、`next start` が JS・CSS を毎回 gzip する分で、圧縮を止めると約 10.5 ms に下がった。人が一度に集まると待ち行列が積もる（手元でも、同時 500 人の HTML だけで最大 25 秒待ち）。
- **（副）メモリが増える。** 同時 1000 人で手元は約 860 MB。B1 の RAM は約 1.75 GB。
- **（副）Health Check が無い。** 応答しなくなっても、Azure が検知して入れ替えない。
- **API は関係しない見込み。** API は 50 件同時で、すべて 200・0.7 秒以内。
- 「共有ページの HTML を毎回描くこと」自体は主因ではない（枠を静的にしても 39 → 36.5 ms）。

## 3. 対策案（案。採否は決まっていない）

| 案 | 中身 | 効き目（手元の見込み） | 運営への相談 |
| --- | --- | --- | --- |
| A | `compress: false`（1 行） | CPU が約 1/4。送るバイト数は約 3 倍 | 不要 |
| B | 共有ページの枠を静的に | 単独では 39 → 36.5 ms。A と合わせて約 1/6.5 | 不要 |
| C | Health Check を有効に（PM の手作業） | 止まったら自動で入れ替える保険 | 不要と見るが PM が判断 |
| D | Always On を有効に | 起動待ちを防ぐ。今回の主因には効かない見込み | 不要 |
| E | 台数を増やす | 限度が台数に比例 | 必要（費用） |
| F | CDN を前に置く | 最も効く | 必要（外部サービス） |

調査のおすすめは「A + B を先に、C と D を同時に」。この記事を書いた時点で、どれを採るかの決定の記録は見つけていない。

## 4. 確認が残っていること（PM の Azure 確認待ち）

- 11/24 の発表時間帯の、プランの CPU・メモリ、アプリの Http 5xx・応答時間。CPU が 100% に張り付いていれば主因が確定する。
- Always On の状態と起動コマンド。同時に何人が開いたか。

## 5. 限界

- 負荷をかけた PC と受ける PC が同じで、B1 とは性能が違う。見られるのは版どうしの相対だけ。
- 「B1 は手元より 3 倍遅い」は仮定で、測っていない。
