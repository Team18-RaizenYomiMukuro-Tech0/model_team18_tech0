# 週1要約ルーティン（AI版・/schedule から実行）

この文面を `/schedule` のクラウドルーティンに登録して、毎週1回 `<リポジトリ名>` で実行する。
機械版（`scripts/weekly-digest.py`）と違い、クラスタリングと原因・直し方の記入を**AIの判断**で行う。

---

## ルーティン本文（これを /schedule に貼る）

あなたは <リポジトリ名> の書記です。週1のナレッジ要約を行います。日本語で。

1. `01_ナレッジ/_inbox/mistakes.jsonl` を読む（無ければ「今週は記録なし」で終了）。各行は1回のエラー記録（マスク済み）。
2. **意味で束ねる**: コマンド・エラー内容が本質的に同じミスは1つの「型」にまとめる。エラー先頭行の文字列が違っても、原因が同じなら同じ型にする（例: 同じ環境変数未設定が別メッセージで出た等）。
3. 各型について `01_ナレッジ/mistakes/<kebab-slug>.md` を作成/更新する。既存があれば発生回数を積み増し、最終発生日を更新。本文の形式:
   - frontmatter（title/type: knowledge/origin: internal/tags: [mistake, (deploy)]/created/updated）
   - 発生回数・最終発生日・収集源・デプロイ系か
   - 症状（代表的なエラー）・実行コマンド
   - **原因**: ログから推定して具体的に書く（分からなければ「要確認」と残す）
   - **直し方 / 再発防止**: 次に踏まないための手順。デプロイ系ならチェックリスト項目も1行で示す
4. `01_ナレッジ/index.md` を全型の目録に更新（発生回数の多い順）。
5. `01_ナレッジ/deploy-checklist.md` を再生成: デプロイ系の型から「デプロイ前に確認すること」を箇条書き（各項目に根拠の型ファイルへのリンクと発生回数）。
6. `CLAUDE.md` の `<!-- auto:mistakes start -->`〜`<!-- auto:mistakes end -->` を、**発生2回以上の型だけ**で更新（このブロックだけ書き換える。他は触らない）。
7. `01_ナレッジ/log.md` に `## [YYYY-MM-DD] 還元 | 週1要約（新規N件→型M件）` を追記。
8. 処理済みの `_inbox/mistakes.jsonl` を `_inbox/archive/mistakes-<日時>.jsonl` へ移動する（inbox を空にする）。
9. 作業ブランチ（例 `chore/knowledge-digest-<日付>`）を切り、`01_ナレッジ/` と `CLAUDE.md` の変更だけを add → commit → PR を作る（main直push禁止）。`_inbox/` はコミットしない（.gitignore 済み）。

## 守ること
- 生ログに秘匿情報が残っていたら、記事に写す前にマスクする。
- 新しい事実を作らない。ログにある事実と、そこからの推定（「要確認」と明記）を分ける。
- 原因が不明な型は無理に埋めず「要確認」で残す。
