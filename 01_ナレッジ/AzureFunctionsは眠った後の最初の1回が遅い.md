# Azure Functions は眠った後の最初の 1 回が約 3 秒遅い（Issue #721。2026-11-25）

origin: internal ／ 根拠: Issue #721（Terao の調査。コードは未修正）。PM の決定 11/25（りじちょーの依頼文で受けた）

## 1. 起きたこと（事実）

- 詳しい情報の API（`/api/products/<ID>`）が、最初の 1 回だけ画面側で約 3.3〜3.6 秒かかった。
- 同じ呼び出しの `Server-Timing` の `total` は 0.42〜0.51 秒。差の約 2.9 秒は API の外。
- DB を使わない `/api/health` も 3.3〜3.6 秒。応答の `proc` は `nth=1`・`up≒1.2s`（起動直後の新しいプロセスの最初の応答）。数分後は同じ詳細が 0.614 秒（`nth=2`）。
- 詳細の SELECT は 1 本。メモリの `catalog`（D-50）は使っていない（D-04 の対象外）。

## 2. 見立て（意見）

- 主因は Azure 側の台・プロセスの起動（約 2.9 秒）。API の中ではない。
- 眠った後の最初の 1 回が遅いのは、Always-ready instances が 0 の設定と合う。**ただし、3.3 秒の内訳（台の起動かプロセスの起動か）は未測定。** Azure の記録が要る。
- 上乗せ: 池は 4 本まで・起動時に先に作るのは 1 本。同時の呼び出しが 2 本以上だと、残りは新しい接続（本番 `db_connect=972 ms`）。DB 1 往復は約 0.2 秒。

## 3. 案と PM の決定

- 案 A: Always ready instances を 1 にする（費用増。PM の操作）。**PM の決定 11/25: 実施しない。**
- 案 B: 画面を開いた時に `/api/health` を 1 回先に呼ぶ。
- 案 C: 詳細もメモリを使い、残す接続を増やす（D-04・D-50 の変更。PM 承認が先）。
- B・C を採るかは、決定の記録を見つけていない。A を採らない理由は、PM の言葉としては残っていない。

## 4. 気をつけること（yamapi の提案。決定ではない）

- 眠った後の最初の 1 回が約 3 秒遅いのは、今の設定では起こりうる。速さの検査（NF-01 の 2 秒）で最初の 1 回を測る時は、眠った後かどうかも記録すると、遅さの理由を取り違えにくい。
