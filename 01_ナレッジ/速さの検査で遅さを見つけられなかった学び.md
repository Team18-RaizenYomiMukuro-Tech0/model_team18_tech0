# 速さの検査で遅さを見つけられなかった学び（D-04・ADR-023。2026-11-25）

origin: internal ／ 根拠: 検索の高速化の調査 PR #710、直しの設計 PR #714、測定 PR #716、実装 PR #718、`02_プロジェクト/giftia-ui-renewal/ADR.md` の ADR-023、りじちょーの Artifact（`review1124/index.html` の「検索の高速化」の節。整理はりじちょーの意見）

## 1. 起きたこと（事実）

- 検索のたびに、DB から商品と購入回数を全部取り直していた。送別だけで 3,643 行、キーワード検索で約 7,800 行。時間の 8〜9 割が SQL だった（#710）。
- 速さの検査 NF-01（送別・3,000〜4,999 円の 1 条件を 10 回測り、2 秒以内か）は合格していた。本番の実測は 1.8 秒前後だった（Artifact の記述）。遅さの形は、検査では見つからず、社長の宿題（Issue #707）の調査で見つかった。
- 直し方（ADR-023。PM 決定 2026-11-25）: 商品の行と回数の集計を、台のメモリに 30 分置く。期限切れは古い値で先に返し、読み直しは裏で 1 回。空の間（起動したて）は今の DB 直の道で返す。測定（#716）で、回数の集計は最大 6.8 秒、起動したての 1 回ぶんは手元で 6.3〜7.9 秒だったため、空の間の道を足した。メモリは約 100 MB で、本番の台の 512 MB に収まる（PM が Azure で確認）。実装は #718（pytest 264 passed）。

## 2. 検査で見つけられなかった理由（りじちょーの整理。4 点）

1. **時間だけを測っていた。** 1 回の検索で何行を読んだかは記録していなかった。12 件を出すのに 3,643 行を読んでいても、2 秒に収まれば合格になる。
2. **今の件数だけで測っていた。** 商品は約 8,000 件の架空データ。商品がもっと多い場合は、検査の条件に入っていなかった。
3. **余裕を見ていなかった。** 2 秒の基準に 1.8 秒で、余裕は 1 割。合格か不合格かだけを見ると、ぎりぎりでも気づけない。
4. **設計に規模の前提が無かった。** D-04 は「回数は保存せず都度数える」と決めたが、何件までならそれで足りるかは書いていなかった。

## 3. 次の設計で考えること（4 点）

1. **件数の前提を数字で書く。** 今の件数と、目指す件数（10 倍・100 倍など）を書き、その件数で 1 回の検索が何秒になるかを見積もる。
2. **1 回の要求の仕事の量に上限を決める。** DB に聞く回数と読む行数の上限を、画面に出す件数と並べて書く（例:「12 件を出すのに読むのは 1,000 行まで」）。
3. **データが変わる速さを、データごとに書く。** 商品はほとんど変わらない・回数はゆっくり変わる・カートは毎回変わる、と分ければ、手元に置いてよい物と許せる古さが設計のうちに決まる。
4. **起動したてと、大勢が同時の時を分けて考える。** 1 人が 1 回使う時だけでなく、サーバーが起きたばかりの時と、発表中のように大勢が同時に開く時の動きを書く。

## 4. 確かめる仕組みにする案（5 案。**まだ案。チームで採否を決めていない**）

- **設計の型:** 5 文書の設計の型に「件数の前提と仕事の量」の節を足す。空のままなら PR テンプレート記入の CI で止める。
- **数えるテスト:** 1 回の要求で DB に聞く回数と読む行数を数える単体テストを API ごとに置き、上限を超えたら CI で落とす。D-04 の U-112 がこの形の最初の 1 本。
- **大きいデータ:** 手元のテストで、商品を 10 倍にした架空データでも測る。本番の DB には足さない。
- **余裕の印:** 速さの検査で、基準の 8 割（2 秒なら 1.6 秒）を超えたら「注意」と出す。
- **内訳を記録:** 応答に DB の時間と読んだ行数を載せ（`Server-Timing`）、速さの検査で一緒に残す。
