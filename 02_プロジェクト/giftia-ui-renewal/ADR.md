## ADR-001 — 成功の定義（購入率の目標値）

- 起点: 要求ID R-01（成功の定義）
- 目的: 経営陣への提案で示す改善見込みを、根拠のある数値にする
- 判断基準: ケースの社内実績値で説明できること。ベンダー公表値に頼らないこと
- 確認した事実: 購入率 3.0%（一般 EC 約2.0〜2.5%）、カート放棄 41%（一般 約70%）。導線別購入率は検索結果 2.4%・特集記事 4.1%。詳細は `inputs/キックオフ記録.md` #7〜8-2
- 採用案: 全体購入率 3.0% → 約3.5%（対象者 A の訪問の40%が新導線を使い、+71% の効果）
- 他案の扱いと理由: 3.8%（前年並み回復）は利用率約67%が前提で根拠が弱いため取り下げ。幅（3.2〜3.7%）は採らず
- 影響する文書・実装・テスト: 要求.md R-01。受入基準には使わない（デモは利用者テストをしないため）
- 決定者・日付: レージ、2026-11-07（回答「B」）
- 状態: 決定（2026-11-07 再決定。下記「再決定」が現行）
- 見直す条件: 利用率や効果の根拠となる新しいデータ（ケースの追加資料、類似施策の実績）が出たとき
- 再検討の理由: 伸び幅 +71%（特集記事経由の購入率）は、りじちょーが置いた仕組みで、本人の設計（途中の脱落率を下げる）と食い違っていた。本人の指摘「特集記事の話はズレているのではないか？」を受け、脱落段階ベースで試算し直す

### 再決定（2026-11-07、レージ、質問13「B」）

- 対象者を共同購入者（職場の送別など）に絞った（質問12）。送別だけでは全体への寄与が小さい（訪問18%×1.7%＝0.31pt）
- 採用案: 全体購入率 3.0% → 約3.5%。送別以外の「仲間で出し合う贈り物」にも同じ解決策が効く前提
- 式: 送別 18%×(3.0−1.7)% ＝ +0.23pt ／ 友人・家族の誕生日（53%、購入率加重 約2.6%）のうち共同購入の割合 g に同じ伸び +76% → (0.812+0.552)×g×0.76。3.5% に必要な g ≈ 26%
- 仮定（根拠なし）: 送別の購入率が全体平均 3.0% まで上がる／友人・家族の誕生日の約4分の1が共同購入。ケースに共同購入の割合のデータは無い
- 他案: 送別を主目標にして全体は約3.2%（A）、段階で分ける（C）は不採用
- 見直す条件: 共同購入の割合が分かるデータ（注文の配送先・メッセージ、ヒアリングの追加）が得られたとき

## ADR-003 — 「無難な理由」のデータ源（既存の列だけ）

- 起点: 要求ID R-01（AC-02 の理由1行）
- 目的: 仲間の同意の材料になる理由を、誤りなく出す
- 判断基準: 作業負担が小さいこと。誤った理由を出さないこと

- 他案の扱いと理由: 新しい属性タグ＋生成AI（ローカルで抽出して DB 反映）は、一度「B+C」で決めたが取り消し。作業負担への懸念から
- 影響する文書・実装・テスト: 要件（理由の種類）、仕様（理由のルール）、テスト（理由の判定）
- 決定者・日付: レージ、2026-11-07（「今ある情報だけで」→「解釈２」）
- 状態: 決定
- 見直す条件: 既存の列だけでは同意の材料にならない（理由が作れない商品が多い）と分かったとき

## ADR-004 — 外部公開（アプリを Azure に置き URL で公開）

- 起点: 一括確認2 #9、CLAUDE.md「本番で動くものを出すのが必達」とケース Exhibit 5「本番公開は対象外」の食い違い
- 目的: 本番で動くものを出す
- 判断基準: 本人の意向。CLAUDE.md の決まり（外部公開は運営の承認後）
- 確認した事実: DB は班の Azure 上の MySQL `giftia_t501`（架空データ）。アプリは Next.js ＋ FastAPI。運営の回答（2026-11-08。`inputs/運営回答_2026-11-08.md`）で、次の範囲と条件で承認された
- 採用案: アプリも Azure の無料のプラン（F1）に置き、URL を知っている人だけが開ける形で公開する。DB は Azure の班 DB に接続
  - 期間: 11/12〜12/12。12/12 に App Service を止め、作ったリソースを削除する（全員）。公開は main ブランチからだけ
  - 検索エンジンに載せない: `robots.txt` で全拒否、`X-Robots-Tag: noindex`。API は画面のドメインからの通信だけ受け付ける（CORS）
  - URL は 〜.azurewebsites.net（独自ドメインは買わない）。データは授業のサンプル（架空）だけ
  - 配置: コードのままデプロイ（コンテナは使わない）。Application Insights はオフ。Azure のログは追加でオンにしない。uvicorn は `--no-access-log`
  - DB: 案A。アプリ用 `giftia_app` は作らず、公開版も配られたアカウントで班の DB につなぐ。管理用アカウントも作らず、CREATE・DROP・テスト行の削除は配られたアカウントで手で。パスワードは Azure のアプリの設定（環境変数）に置き、リポジトリには入れない
  - 案A の理由: 配られたアカウントに CREATE USER・GRANT が無く `giftia_app` を作れない（`DB管理手順.md` 穴4）。運営のだーあさに確かめ、「承知しました」と回答があった（根拠: `inputs/運営回答_2026-11-08.md` の追記、キックオフ #68・#70）。レージの判断は「デモデータだから壊れても問題ない」
  - 案A の影響: 権限を DB で絞れない。ほかの班の `giftia_t502`〜`t506` も書き換えられるアカウントを Azure に置く。漏れたときは運営に連絡してパスワードを替えてもらう。代わりにコードで3つ縛る（接続先は `giftia_t501` に固定・書き込みは `share_links` への INSERT だけ・SQL はすべてプレースホルダ。設計 D-13）
  - 作成回数の制限は作らない（#73）: 公開期間（11/12〜12/12）中、URL を知る人は `share_links` に行を何度でも足せる。守りは「URL を知る人だけ」「架空データ」「12/12 に表ごと消す」の3つ
  - DB の接続（#71）: 接続先は `giftia_t501` をコードに定数で固定し、DB 名は環境変数で受けない。SSL は certifi の公開の証明書の束を使いホスト名を確かめる（証明書ファイル・環境変数は使わない）。確認済み（Terao が手元から接続。TLSv1.3。証拠: `evidence/db/2026-11-08_ssl-certifi.md`、版 fc3e84e）。つながらなくなったら、証明書の中身（PEM）を Azure のアプリの設定の環境変数に置き起動時に書き出す形（案P）に戻す
  - 実機確認: 公開後に iPhone（Safari）で共有ページを1回。Android（Chrome）は実機を使わず、公開前の PC の Chrome 幅縮めで代える（Android の実機が手元に無いため、りゅうちゃん 2026-11-14。PM 判断: だーあさ OK 2026-11-14（Slack））。確認用のリンクは当日中に手で消す
  - 費用: 見込み0円。週に1回、すべて無料のプランのままか確かめる。見られれば予算アラート（例 500円）
- 他案の扱いと理由: 手元の PC だけで動かす案は、本人が外部公開を選んだため不採用
- 影響する文書・実装・テスト: 設計（D-16、D-19、D-33）、N-07・N-08・N-11・N-13、計画（発展項目、Azure への配置など）、テスト設計
- 決定者・日付: レージ、2026-11-07（「外部公開する！」）。運営（だーあさ・りゅうちゃん）の承認、2026-11-08（キックオフ #65）
- 状態: 決定（運営の承認済み。上の範囲だけ）。着手は実装計画の「OK、進めて」の記録の後
- 見直す条件: 運営の承認の範囲を超える設定が要るとき、または無料のプランで動かないとき
- **変更（2026-11-11）**: 置き場所が「自分で作る F1 の App Service」から「講師が作って配るリソース（API=Azure Functions Flex 従量課金・Python 3.14、画面=App Service Node 24）」に変わった（講師の手順書 `release-guide-13ki-v1` による）。設計 D-33 の「運営が用意した枠があれば、そちらを優先する」に当たる。
  - 理由: 講師がリソースを用意して配ることになったため。
  - 影響: ①プラン（F1）を自分たちで選ばない。リソースの費用・設定は講師の管理範囲で、週1回の無料の確認と予算アラートは行わない（要件 N-08、テスト設計 NF-17 を廃止）。②API は Functions（uvicorn を使わない）なので、`--no-access-log` に頼る書き方はやめる。アプリ自身のログに IP を残さない点は変えない。Functions 側のログ（利用者の IP が残るか）は講師の管理範囲。③講師のリソースに Application Insights が付いていても、講師の管理範囲としてそのままにする。④12/12 のリソースの停止・削除は講師側。班の DB の中身（`share_links` の削除など）の片付けは今までどおり自分たち。⑤Python 3.14 での実行は未確認（リソースが届いてから）。
  - 決定者・日付: PM 本人の回答、2026-11-11（ログは講師側・Application Insights は講師の管理範囲として明記・リソース削除は講師側・文書と Issue の更新を Takahiro に依頼）
  - 上の「採用案」の F1・`--no-access-log`・「作ったリソースを削除する（全員）」は、この変更で読み替える（当初の記録として残す）。

## ADR-006 — 候補 API の常時起動は入れない（NF-01 は未達の見込みのまま評価に出す）

- 起点: NF-01（候補 2 秒）、Issue #256（T3b）、PR #258・#260・#261・#265
- 目的: 候補 API の速さの残りの遅れに、お金と運営への相談をかけるかを決める
- 判断基準: デモサイトであること。運営のサブスクリプションに費用が出ること
- 確認した事実（根拠は #256 の Terao のコメント。2026-11-14、本番、GET のみ）:
  - #258 で DB の接続を使い回し、本番の候補取得は 4.3〜4.7 秒 → 0.9〜2.1 秒になった（接続の作り直しは 0 回）
  - 残りの遅れは「要求ごとに新しいプロセスが起動する待ち」約 0.84 秒。20 回中、新しいプロセスの最初の応答は 14 回で、待ちはその 14 回すべてに出て、それ以外には出なかった
  - 原因の見立て: Flex Consumption の常時起動のインスタンスが 0 台（Azure の設定は確認していない）
  - DB との 1 往復は約 0.2 秒。索引で削れるのは約 0.1 秒どまり
- 案:
  - A. 送別回数を覚える: 新しいプロセスでは覚えがゼロなので、B なしでは効かない
  - B. 常時起動 1 台: 月約 5〜21 ドル。運営のサブスクリプションなので運営への相談が要る。約 0.84 秒が消える見込み（価格帯ありで約 1.8 → 約 0.95 秒）
  - C. 索引: 約 0.1 秒
- 採用案: 入れない（B・A・C のどれも今は実装・設定しない）。理由: デモサイトだから
- 他案の扱いと理由: B は費用と運営への相談が要るため見送り。A は B なしでは効かないため見送り。C は効果が小さいため見送り
- 影響する文書・実装・テスト: 要件の数字は変えない。NF-01 は価格帯なしで未達の見込みのまま評価に出す。評価で聞かれたら「本番なら常時起動で約 1 秒」と説明する（この数字は B を入れた場合の見込みで、実測ではない）
- 決定者・日付: PM（だーあさ）、2026-11-14（原文「デモサイトなので、やらないことにしましょう。」）
- 状態: 決定
- 見直す条件: 運営が常時起動の費用を認めたとき、またはデモの利用者が増えて速さが問題になったとき

## ADR-008 — 欄の名前を「贈った人の声」にする（「使った人の声」にしない）

- 起点: 第2弾の企画 P（だーあさ案「決め手と贈った人の声」）、要件 F-22、仕様 SP-17
- 目的: 誕生日に贈る人（D さん）が「相手に喜ばれるか」を確かめる材料を、データの事実に合う言葉で出す
- 判断基準: 値を作らないこと（OPEN-06）。データに無いこと（使った後の感想）を、あるように見せないこと
- 確認した事実: 班の DB の `reviews` にある声は、贈った側の感想だけで、使った後の声は無い。本文があるのは 30%（24,751 件中 7,419 件）。誕生日の商品で声が 2 件そろうのは 9.7%（どちらも Terao 調べ、2026-11-13、SELECT のみ。企画ページ「第2弾の企画」の注記）。架空データには、商品とシーンが合わない声がある（例: ハンドクリームに「出産祝いに」）
- 採用案: 欄の名前は「贈った人の声」（決定 2026-11-13）。`reviews` の実際の文を、星 4 以上・本文あり・新しい順・同じ文は 1 回・最大 2 件のルールで出し、0 件なら欄ごと出さない（仕様 SP-17）。商品とシーンが合わない声は今回は除かない
- 他案の扱いと理由: 「使った人の声」は、DB の声が贈った側の感想だけなので採らない。声の文を作る・要約する案は、値を作らない決まり（OPEN-06）と生成 AI を使わない決まり（ADR-003）に反するので採らない
- 影響する文書・実装・テスト: 要件 F-22・N-13、仕様 SP-17、設計 D-35（`reviews` を読み取りだけ）、テスト U-62〜U-66・I-43・I-44・S-75・A-14

## ADR-011 — 計測は班の DB に自分で記録する（計測の道具を入れない）

- 起点: 第2弾の計測 M、要件 N-16、仕様 SP-34、設計 D-40・D-41
- 目的: 事業インパクトの漏斗（訪問→カート→購入）を、自分たちのサイトで測れるようにする
- 判断基準: 運営の承認の範囲だけ（追加の外部サービスは運営への相談が要る。CLAUDE.md）。費用を足さない（N-08）。個人の情報を集めない（N-13）
- 確認した事実: 今の班の DB（`orders`）で数えられるのは購入の件数だけで、訪問・詳細・カートの通過は残っていない（企画ページ「事業インパクト」の補足）。計測の 2 案は、測る段が同じで記録を置く場所が違う（企画ページ「決めること 4 の材料」）
- 採用案: 案A。班の DB に新しい表 `usage_events` を作り、画面から 6 段（① サイトに来る ② 検索結果を開く ③ 詳細を開く ④ カートに入れる ⑤ 共有リンクを作る ⑥ 注文へ進む）を記録する。分母は訪問（30 分で区切る）。持つ項目: 訪問の ID・匿名の訪問者 ID（ブラウザ内の乱数）・段・時刻・シーン・声の有無・入口・0 件の条件・テストの印。持たない項目: 名前・メール・IP アドレス・ブラウザの情報・商品 ID・検索語・ユーザー ID。記録は評価が終わるまで残し、発表の後に消す（M-2）。通過率は「その段の記録がある訪問の数」で数え、段の順番は数えない（案）
