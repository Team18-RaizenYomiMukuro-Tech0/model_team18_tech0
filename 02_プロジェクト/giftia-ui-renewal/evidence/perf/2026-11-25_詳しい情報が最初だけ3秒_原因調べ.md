起点: main `b43bca7`。コードは直していない。DB は SELECT だけ。本番 API は 1 本ずつ約 20 回。接続情報は表示していない。

## 1. コードの事実

## 4. 見立て
1. **最大の原因（約 2.9 秒）**: Azure Functions（Flex 従量課金）の「台・プロセスの起動」。応答に `nth=1`・`up≒1.2s` が出る回はいつもこの約 3 秒が乗る。設計.md D-45 の「起動したての回」（約 5 回に 1 回、API の外が約 3 秒）と同じ型。今回は並んだ呼び出しのうち 4 本が新しい台に当たり、2 本（0.213 秒）が起動済みの台に当たったと見ている（私の推測。Azure の記録で確かめたい）。
2. **上乗せ（約 1 秒）**: 池は 4 本まで、起動時に先に作るのは 1 本。新しい台は 1 本目しか接続を持たないので、同時の呼び出しが 2 本以上あると、残りは新しい接続（約 1 秒。本番の `db_connect=972 ms`）を作る。
3. **常に乗る**: DB への 1 回の往復が約 0.2 秒（本番の `db_sql=223 ms`）。班の DB が遠いように思える。
4. 詳細の API は D-04 のメモリを使わないので、一覧・候補が速くなっても詳細は DB 直のまま（SQL 約 0.2 秒）。ただし 3 秒の主因ではない。

測れていないこと: 3.3 秒のうち台の起動とプロセスの起動の内訳（Azure 側の記録が要る）。同時 6 本を本番で再現していない（負荷禁止のため）。

## 5. 直す案（コードは直していない）
- **案 A（Azure の設定。PM）**: 常時起動のインスタンス（Always ready）を 1 にする。起動の約 3 秒が無くなる見込み。費用が増える。
- **案 B（画面）**: 画面を開いた時に `/api/health` を 1 回だけ先に呼び、台を起こしておく。費用は増えないが、起こせるのは「最初の 1 台」だけ。
- **案 C（API）**: 詳細もメモリを使う（description・size を `catalog` に足す）＋起動時に残す接続を 1 本から増やす。約 0.2 秒と約 1 秒の上乗せを減らせるが、3 秒の主因は残る。仕様（D-04・D-50）の変更なので、PM の承認が先。

## 6. PM が Azure で見てほしい物
1. 関数アプリ `func-gen13-step3-5181` の「Always ready instances」の設定値（今は 0 か）。
2. Application Insights（または Log stream）で、11/25 18:45〜18:55 JST ごろの `/api/products/*` の要求。`Host started`・新しいインスタンス起動の記録が、遅い要求の直前に出ているか。
3. 「Scale and concurrency」の HTTP の同時実行数（既定値か）と、その時間帯のインスタンス数の推移。
