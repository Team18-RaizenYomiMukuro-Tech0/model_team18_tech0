## 1. 結論

- **配分は目安とずれています。** テスト設計の ID は「システムが最多」（単体 33%・結合 22%・システム 45%）で、70:20:10 を逆にした形です。コードの本数は「単体 77%・結合 23%・システム 0%」で、下の 2 段は目安に近く、一番上の段が自動で守られていません。
- **画面のテストが自動化されていません。** 画面の部品（`.tsx` 47 ファイル、3,428 行）を描画して確かめるテストは 0 本です。システム S 145 行は、人と使い捨てのスクリプトで回した結果です。
- **受け入れ方針は「自分たちで作って、自分たちで判定する」形です。** 受入 A は、対応する S が全部 ○ なら ○ と数える集計で、独立した確認になっていません。

発表の答え「単体・連結を全て通ったものだけを出している」は、本数では正しいです。ただし次の 2 点を足して言うのが正確です。DB につなぐ結合テスト 19 本は CI で skip されます。初回提出版（`285f836`）には × が 5 件ありました（#240 で直す）。

## 2. 数え方

**設計の数え方。** `テスト設計.md` の表の行頭にある ID を、見出しの節ごとに数えました。重複は 1 件に数えています。

**コードの数え方。** 区分の基準は 3 つです。

- **単体:** 1 つの関数・モジュール・状態の部品を、外とつながずに呼ぶテスト。HTTP の入口（`TestClient`）も、DB への接続も使わない。
- **結合:** API を HTTP の入口から呼ぶテスト（`TestClient`）、または DB につなぐテスト。偽の DB を差し込んだものも、入口から呼ぶなら結合に入れる。
- **システム:** ブラウザで画面を動かして確かめるテスト。リポジトリには 0 本。

backend の区分は、テスト関数の本文に `client`・`TestClient`・`client_for`・`function_app` が出るか、DB 接続・skip の記述があるかを自動で見分けました。目安の精度で、±10 本ほどの揺れがあります（`\bapp\b` を判定に入れると結合 149・単体 119、外すと結合 139・単体 129。表は後者）。frontend は React の描画・DOM を使うテストが 0 件で、全部が関数と状態の単体です（偽の `fetch` を差し込むテストが 7 ファイルありますが、HTTP の入口を呼ばないので単体に入れました）。

## 4. 目安との差

目安は 70:20:10（単体:結合:システム）を使います。これは本数の目安で、決まりではありません。

| | 単体 | 結合 | システム |
| --- | ---: | ---: | ---: |
| 目安 | 70% | 20% | 10% |
| 設計の ID（U・I・S） | 32.7% | 22.5% | 44.8% |
| 自動のテストコード | 76.6% | 23.4% | 0% |
| 差（コード − 目安） | +6.6 | +3.4 | −10 |

読み取れること:

1. **設計の ID は、システムに偏っています。** S は 145 行で、U の 1.4 倍あります。画面の状態・幅（375px・1280px）・演出を 1 行ずつ書いたためです。
2. **コードは、下の 2 段に偏っています。** 単体 454・結合 139 は目安に近い形です。システムの自動テストが 0 なので、画面と API のつなぎ目は人が回した結果だけが根拠です。
3. **画面の部品に自動テストがありません。** `src/components/`・`src/app/` の `.tsx` 47 ファイルに、描画のテストが無いです。表示の崩れ・押したときの動きは、回帰（直したあとに別の所が壊れること）を自動で見つけられません。
4. **実 DB を使う結合 19 本は、CI で回りません。** SQL の誤りは、人が班の DB で回すまで見つかりません。
5. **受入 A は、数を水増ししています。** A の 28 行の大半は S の再掲です。割合に入れると、受入が 6.6% あるように見えますが、独立した確認は 3 行（A-01・A-02・A-28）です。

## 5. おすすめ（足す・減らす）

数の比率に合わせて数を増やすのは勧めません。70:20:10 に合わせるには、システムを約 66 本（全体の 10%）に増やす計算になりますが、画面の自動テストは 1 本ずつの費用が高く、割に合いません。**危険の大きい流れから、少数を自動にする**のがおすすめです。

**足す案（理由つき）。** どれも、新しい道具を入れる場合は PM（運営）の承認が先です。

### 6.2 穴

1. **作った人が受け入れています。** 判定の根拠は、評価版の S と、チーム自身のデモ操作です。外の利用者が確かめた証拠は無いです。
2. **受入基準が S の再掲です。** A が独立した確認になっていません。S が間違っていれば、A も同じ間違いを受けます。
3. **範囲が不揃いです。** 2026-11-21 の受入判定は AC-01〜AC-12 です。AC-13〜AC-27（第2弾）の受入判定の記録は、この調査では見つけられませんでした。A-28 は PM が判定しました（#541）。
4. **「受け入れない」ときの決まりがありません。** × が出たとき、誰がいつまでに直し、再判定するかの手順が無いです。
5. **DB・CI に頼る部分の扱いが不明です。** 実 DB の結合 19 本が skip されることは、受入の条件に書かれていません。
6. **AC-11 は ○ ですが、自己評価は「一部できた」です。** 本番では 0 件になる条件を見つけられていません。PM が理由を添えて ○ と決めました（2026-11-21「Aで」）。

### 6.3 直し案

1. **受入を 3 段にします。** ① 自動（U・I・自動の通し確認）が全部 ○ → ② S の判定が ○ → ③ PM のデモ操作。③ は A-01・A-02・A-28 のような、通しの操作だけにします。
2. **受入の条件に、数字を書きます。** 例「自動テストの pass 数と skip 数を提出版に書く」「skip がある場合は、理由と、回す日を書く」。
3. **作った人以外の目を 1 回入れます。** 利用者テストが無理なら、作っていない人が、S の中の主要 5 流れだけを自分の手で通します。
4. **× のときの手順を足します。** 例「× を出した人が再現手順を書く → 実装担当が直す → 同じ行だけを再度回す」。
5. **範囲を表にします。** AC ごとに「判定した日・版・誰が」を 1 表にします。第2弾（AC-13〜27）の行が空欄なら、その旨を残します。
