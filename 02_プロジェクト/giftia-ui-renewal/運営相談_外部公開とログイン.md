# 運営への相談 — 外部公開・ログイン・DB・費用の確かめ方

チーム18 / 案件: Giftia UI/UX リニューアル / 起票: りじちょー、送付: レージ（2026-11-08 版）
関連: `ADR.md` ADR-004（外部公開）、`要求.md` OPEN-05（ログイン）、`要件.md` N-04・N-08・N-09・N-11・N-13、設計.md 未決 M、テスト設計 H-16・H-21

CLAUDE.md の決まり（認証・外部公開・実データ・追加の外部サービスは、実装・設定・公開の前に運営へ相談し、承認された範囲だけ進める）に従い、次の7点をまとめて相談します。**承認までは、手元の PC での開発とテストだけを進めます。**

## お願いの一覧（何を許可してほしいか）

| # | 相談 | 許可してほしいこと（1行） |
| --- | --- | --- |
| 1 | 外部公開 | アプリ（Next.js と FastAPI）を Azure に置き、URL を知っている人が開ける形で公開してよいか |
| 2 | ログイン | ヘッダーのログイン入口の中身（認証）を実装してよいか、よい場合は使ってよい方式 |
| 3 | DB のアカウントと権限 | 班の DB にアプリ用の読み取り中心アカウントを追加し、テーブル作成・削除を管理用アカウントで手で行ってよいか |
| 4 | 基盤側のログ（未決 M） | Azure 側のログに IP アドレスが残るかを確認し、残る場合の扱い（保存期間・設定）を教えてほしい |
| 5 | 実機での確認 | 公開した URL を iPhone（Safari）と Android（Chrome）の実機で1回ずつ開いて確認してよいか |
| 6 | 共有リンクの URL の頭 | 公開 URL（ドメイン）を決めてよいか、または指定のドメインを教えてほしい |
| 7 | 費用の確かめ方 | 開発段階の費用が 500 円以内かを確かめるため、Azure の請求・コストの画面を見る権限をもらえるか |

## 相談1: アプリの外部公開

| 項目 | 内容 |
| --- | --- |
| 目的 | 共同購入者が、候補をまとめた共有リンクを仲間（Giftia を使わない人）にスマホで見せられることを、本番に近い形で確かめる |
| 公開するもの | Next.js（フロントエンド）と FastAPI（バックエンド）のアプリ。URL を知っている人が開ける |
| 置き場所（希望） | Azure（使ってよいサービスの種類を教えてください） |
| 使うデータ | 班に配布された架空のダミーデータ（Azure 上の MySQL `giftia_t501`）。実データ・個人情報は使わない |
| 書き込み | 共有リンク用の新しいテーブル1つ（選んだ商品の作成時点の商品ID・商品名・価格・理由の文と、作成日時、テスト用の印。個人情報なし）。既存テーブルは変更しない |
| リスク | 公開 URL から DB に過大な負荷がかかる／共有リンクの識別子を推測される／接続情報の漏れ |
| 対策 | 識別子は推測できない22文字のランダム文字列。リンクは作成から720時間（30日）で期限切れ。検索エンジンに載せない（noindex）。入力は検証し、価格帯は3つの値（under3000・3000to4999・5000plus）、シーンは3つ、カテゴリーは10種だけ受け付け、それ以外は 422 を返す。DB の接続情報は環境変数に置きコミットしない（SSL 接続、証明書とホスト名を検証）。書き込みは共有リンクのテーブルだけ。自サイトの画面以外からの API 呼び出しは許さない（CORS） |
| 公開の期間 | 希望: 評価期間の終わりまで（運営の指定に従います） |
| 戻し方 | 公開を止め、Azure 上のアプリを停止・削除する。共有リンクのテーブルを削除する（既存データには影響しない） |

## 相談2: ログイン（認証）

| 項目 | 内容 |
| --- | --- |
| 目的 | PDF の要求（ヘッダーのログイン入口）に沿って、ログインの中身を作る |
| 現状の方針 | 承認までは、入口に「準備中」と表示するだけ。お気に入り・カートはブラウザ内保存でログイン不要 |
| 相談したいこと | 認証を実装してよいか。よい場合、使ってよい方式（例: 自前のパスワード認証、外部の認証サービス）と、会員データ（ダミーの users）の使い方 |
| リスク | パスワードの保存・漏えい、認可の抜け（他人のデータが見える） |
| 戻し方 | ログイン機能を無効にし、入口を「準備中」に戻す |

## 相談3: DB のアカウントと権限

| 項目 | 内容 |
| --- | --- |
| 目的 | 要件 N-04・N-09 のとおり、アプリが使うアカウントの権限を最小にし、テーブルの作成・削除は別の管理用アカウントで人が手で行う（手順は `DB管理手順.md`） |
| 相談したいこと | 班の DB `giftia_t501` で (1) アカウントを追加してよいか（アプリ用: 既存テーブルは SELECT のみ、共有リンク用テーブルは SELECT・INSERT のみ） (2) 配布されたアカウントに CREATE・DROP・DELETE・GRANT の権限があるか (3) アプリ用アカウントの接続元（ホスト指定）をどう決めるか (4) 追加できない場合、配布されたアカウント1つで進めてよいか |
| リスク | アプリ用アカウントの権限が広いと、不具合や攻撃で既存データを書き換えられる |
| 戻し方 | 追加したアカウントを削除する。共有リンク用テーブルを削除する |

## 相談4: 基盤側のログに IP が残るか（未決 M）

| 項目 | 内容 |
| --- | --- |
| 背景 | 要件 N-13 で、アプリのログには IP アドレスとブラウザの情報を残さない（時刻・API・結果だけ）と決めた。Azure など配置先の側のログに IP が残るかは、公開の承認後でないと分からず、仕様に書かれていない |
| 相談したいこと | 使ってよい Azure のサービスで、アクセスログに IP が残るか。残る場合、保存期間・オフにできるか・運営の決まりがあるか |
| リスク | 個人情報を集めない方針（N-13）と、基盤側のログが食い違う |
| 戻し方 | 公開を止める |

## 相談5: 実機での確認（H-21）

| 項目 | 内容 |
| --- | --- |
| 背景 | 要件 N-11: 共有ページは iPhone Safari と Android Chrome の最新版で見られること。承認前は PC Chrome の幅を縮めて確認するだけで、実機での確認は公開 URL ができてからになる（テスト設計 NF-23） |
| 相談したいこと | 公開後に、メンバーの手持ちの iPhone・Android で共有ページを開いて確認してよいか（1回ずつ。架空データのみ） |
| リスク | 公開 URL を実機に入力・共有するので、URL が班の外へ広まるおそれ |
| 戻し方 | 確認後に公開を止める。確認で作った共有リンクの行は、テスト用の印で後片付けする |

## 相談6: 共有リンクの URL の頭

| 項目 | 内容 |
| --- | --- |
| 背景 | 共有リンクは `/s/{識別子}` で、頭（ドメイン）は公開 URL が決まってから決める。承認前は、画面が開いているサイトの URL に自動でつないでコピーする（設計.md） |
| 相談したいこと | 公開 URL（Azure が付けるドメインでよいか、指定のドメインがあるか）。決まったら環境変数で設定する |
| リスク | 頭が変わると、すでに作った共有リンクが開けなくなる |
| 戻し方 | 公開を止める。共有リンクは720時間で期限切れになる |

## 相談7: 費用 500 円以内の確かめ方（H-16）

| 項目 | 内容 |
| --- | --- |
| 背景 | 要件 N-08: チームが払う費用は開発段階で合計500円以内（#35 8-1）。今は「有料のサービス・設定が無いこと」（テスト設計 NF-16）だけを確かめている。合計の確かめ方（NF-17）は Azure の請求画面などの見方が分からず保留 |
| 相談したいこと | (1) 使ってよい Azure の枠（無料枠・運営負担の範囲） (2) チーム側の請求・コストの画面を見られるか、見られない場合は運営から費用を教えてもらえるか (3) 500 円を超えそうなときの連絡先 |
| リスク | 気づかないうちに有料のサービスが使われる |
| 戻し方 | 有料になったリソースを止める・削除する |
