### API

共通: JSON、文字コード UTF-8。エラーは `{"error": {"code": "...", "message": "..."}}`。

| 設計ID | メソッド・パス | 入力 | 成功時の出力 | エラー |
| --- | --- | --- | --- | --- |
| D-01 | `GET /api/candidates` | クエリ `budget`（**任意**。付けるときは半角数字だけの文字列で、整数に直すと1,000〜999,999、円・総額。全角・カンマ・空白は API では直さない。付けなければ価格で絞らない）、`scene`（`お礼` / `誕生日` / `送別` のどれか1つ） | 200 `{"items":[{"product_id","name","price","category","high_rating","reason"}],"count":n}`。最大10件、順位順（順位＝並びの番号。1から）。`category` はカテゴリー共通イラストの選択用、`high_rating` は評価4.5以上（`HIGH_RATING_MIN`）のとき true（サーバーが数値のまま比べる。4.49 は false）。`reason` は自然な文の1つの文字列。評価はデータの値のまま文に入れる（4.49 は 4.49、4.0 は 4.0。丸めない）。`count` は返した件数。0件は 200 で `items:[]` | 422 入力が不正（`budget` を付けたときの範囲外を含む）／500 DB 障害・想定外 |
| D-05 | `POST /api/share-links` | 本文 `{"product_ids":[…]}`（重複を除いて1〜10件。配列の長さは50まで） | 201 `{"share_id","path":"/s/{share_id}","created_at","expires_at"}` | 422 重複を除いて0件（`empty_selection`）・重複を除いて11件以上、または配列の長さが50を超える（`too_many_items`）・型が不正・存在しない商品ID（`invalid_product_ids`）／500 DB 障害。同じ商品IDの重複はエラーにしない（1件にまとめる） |
| D-06 | `GET /api/share-links/{share_id}` | パスの `share_id`（形式は英大文字・英小文字・数字・「-」「_」の22文字） | 200 `{"created_at","expires_at","items":[{"product_id","status","name","price","reason"}]}`。`status` は `available` / `discontinued` / `out_of_stock`。`name`・`price`・`reason` は作成時点の保存値 | 404 見つからない（形式が不正な識別子も含む）／410 期限切れ／500 DB 障害 |

- 検索を GET にしたのは、読み取りのみ（SP-01 のデータの変化＝なし）のため。
- 順位付けと理由の生成は FastAPI（Python）で行い、SQL では候補の抽出と回数の集計だけをする。
- `POST /api/share-links` の本文は商品IDだけ。名前・価格・理由は**サーバーが作成時点で作り直して保存**する（画面から受けた値を信用しない）。
- 打ち切り（#29-14）: 画面側で検索・作成・表示とも10秒で通信を打ち切り、「失敗しました。もう一度お試しください」と再試行を出す。サーバー側の DB 問い合わせも10秒を上限にする。10秒に達した時点で画面は失敗表示にし、その後に届いた応答は画面に出さず捨てる（#30 J。fetch の `AbortController` で中止し、遅れて届いた結果は反映しない）。
- 作成（`POST`）が打ち切られた後に、サーバー側でリンクが作られることは許す（#30 C。個人情報なし、誰にも見られず720時間で期限切れ）。

### 順位付けの処理（D-01・D-02）

1. 候補の抽出（SQL）: 商品テーブルとシーンタグ（product_scenes）を結び、`シーン＝選んだシーン` かつ `stock ≧ 1` かつ（`budget` があるときだけ）`price ≦ budget` かつ `price × 10 ≧ budget × 7`。70%・100%ちょうどを含む（#29-4）。70%は四捨五入せず、この整数の式で比べる（#30 D）。**`budget` が無いときは価格の条件を付けず、シーンと在庫だけで絞る**（並べ方・理由の文は同じ。#39）。在庫が NULL の商品は「1以上」を満たさないので出さない。
2. 評価の扱い: 評価と件数の**両方**がある商品は R＝評価、v＝レビュー件数。どちらかが無い商品は v＝0（点数＝C）（#29-1）。
3. C ＝ 手順1で抽出した候補のうち、**評価があり、かつ件数が1以上**の商品だけの平均評価（#37-5。評価があっても件数0の商品は含めない＝#32-3 とそろえる）。C に入れる商品が1つも無ければ C は使われず（全員 v＝0 で点数が同じ）、全員同点として手順5の順（送別回数 → 商品ID）で並べる。評価だけ・件数だけが無い商品も v＝0。
4. 点数は分数（Python の `Fraction` か `Decimal`）で計算し、同点を正しく見分ける。
5. 並び: 点数の高い順 → 同点は送別回数の多い順 → なお同じなら商品ID順（#29-2）。上位10件を切り出す。
6. 送別回数の集計（D-04）は、**順位が決まる範囲の商品だけ**を対象にする。手順2〜5のうち、点数（評価と件数だけで決まる）で先に並べ、上位10位の点数以上の商品（上位10件と、10位と同点の商品）の回数だけを数える。同点の並びと理由に使う。予算を付けないと候補が多くなるので、全候補の回数を数えない（待ち時間のため。結果は全候補を数えたときと同じ）。順位付け B では回数は点数に効かない（記録 #29）。

### 予算欄の正規化（D-08・D-01、#32-1）

直すのは**画面**（予算欄）だけ。API は直さず、直した後の半角数字だけの文字列を受ける（直す場所を1つにして、二重に直して食い違うのを避ける）。

1. 全角数字「０〜９」を半角「0〜9」に、全角カンマ「，」を「,」に置き換える。
2. 前後の空白（半角・全角）を除く。
3. カンマ「,」をすべて除く。
4. 残りが半角数字だけで、1文字以上ならば、先頭の0を無視して整数に直す（「０４，５００」→ 4500）。
5. **手順2の後で空（空欄・空白だけ。#41-3）なら、予算なしとして扱い、エラーにしない**（`budget` を付けずに API を呼ぶ。#39）。それ以外（文字・小数点・符号・途中の空白・カンマだけなど）は入力エラー（`invalid_budget` と同じ文言）。画面は API を呼ばない。
6. 直した値が1,000〜999,999の範囲外でも入力エラー。画面は直した整数を `budget` として API に送る（例「４，５００」→ `4500`）。

### 理由の文（D-03）

事実をテンプレートでつなげる（AI は使わない）。値のある材料の文だけを、次の順につなげる（仕様 SP-03、#30 A・E）。

> 例1: 職場の送別で48回選ばれていて、評価も4.6（120件）と高めです。2日で届き、ラッピングもできます。
> 例2: 職場の送別で12回選ばれています。評価は4.2（30件）です。3日で届きます。
> 例3: 職場の送別での購入は、まだありません。評価は4.0（8件）です。2日で届きます。

| 順 | 材料 | 条件 | 文片 |
| --- | --- | --- | --- |
| 1 | 送別回数 n | n≧1 かつ、評価の文があり評価4.5以上（つなぐ） | 「職場の送別で{n}回選ばれていて、」に評価の文（次の行の「評価も」）が続く |
| 1 | 送別回数 n | n≧1 で、上に当てはまらない | 「職場の送別で{n}回選ばれています。」で文を閉じる |
| 1 | 送別回数 n | n＝0 | 「職場の送別での購入は、まだありません。」（0 でも出す。#29-11） |
| 2 | 評価 r と件数 v | 評価も件数もある・件数 v≧1・r≧4.5・つなぐとき | 「評価も{r}（{v}件）と高めです。」 |
| 2 | 評価 r と件数 v | 評価も件数もある・v≧1・r≧4.5・つなぐときでない（n＝0 のとき） | 「評価は{r}（{v}件）と高めです。」 |
| 2 | 評価 r と件数 v | 評価も件数もある・v≧1・r＜4.5 | 「評価は{r}（{v}件）です。」 |
| 2 | 評価 r と件数 v | 評価か件数が無い、または件数が0 | 評価の文を入れない（順位付けも v＝0。#32-3） |
| 3 | 配送日数 d とラッピング | 配送日数あり・ラッピング可 | 「{d}日で届き、ラッピングもできます。」 |
| 3 | 配送日数 d とラッピング | 配送日数あり・ラッピング不可／値なし | 「{d}日で届きます。」（ラッピングの文は入れない。#32-4） |
| 3 | 配送日数 d とラッピング | 配送日数なし・ラッピング可 | 「ラッピングができます。」 |
| 3 | 配送日数 d とラッピング | どちらも無い・不可 | 入れない |

「評価も」を使うのは、送別回数の文が「選ばれていて、」とつながるときだけ（#32-2）。それ以外の評価の文は「評価は」で始める。例: 「職場の送別での購入は、まだありません。評価は4.7（50件）と高めです。」

- 送別回数は毎回数える（0 でも「まだありません」の文になる）ので、理由の文は必ず出る。「材料が全部無ければ価格だけ」は削った（#30 E）。
- 「配送日数なし・ラッピング可」の文（「ラッピングができます。」）は、仕様の例に無く、設計で置いた最小の言い回し。
- 値を作らない。判定は材料ごとの値の有無と、評価4.5以上かどうかだけ。

### データ

**DATA-01 送別回数（保存しない・都度集計）** — 考え方（テーブル名・列名は Exhibit 4 の実物で確認してから決める。未決 1）:

1. 順位付けの手順6で決めた範囲の商品IDの一覧について、注文（注文明細）から `推定シーン＝送別` かつ `送り先＝会社宛て` の行を商品ごとに数える（`GROUP BY` 商品ID、`WHERE` 商品ID IN (…)）。
2. 注文が0件の商品は回数0とする（文は「まだありません」）。
3. 全商品は数えない。候補の商品IDだけに限る（待ち時間のため）。
4. 新しい列・テーブルは足さない（ADR-003）。

**DATA-02 共有リンク（新テーブル `share_links`）** — 既存テーブルは変更しない:

| 列 | 型 | 制約・意味 |
| --- | --- | --- |
| `share_id` | CHAR(22)、文字セット ascii、照合順序 ascii_bin（大文字と小文字を区別） | 主キー。サーバーが暗号用の乱数から作る推測できない22文字。使う文字は英大文字・英小文字・数字・「-」「_」（URL に安全。Python `secrets.token_urlsafe(16)` がこの22文字を返す）。連番にしない（N-02、#30 I）。衝突したら作り直す |
| `items` | JSON | 選んだ商品の一覧 `[{"product_id","name","price","reason"}]`（商品ID・作成時点の商品名・価格・理由）。1件以上10件以下。重複は除き、並びは**最初に出てきた順**（選んだ順＝最初の出現順。共有ページの並びは一括確認8の7で確認中のため、決まるまでこう置く）。作成後は更新しない（SP-07）。テスト設計 R-13・I-06 の項目（商品ID・商品名・価格・理由）はこの列に入る |
| `created_at` | DATETIME（秒まで）、NOT NULL | 作成日時（アプリのサーバー時刻、UTC） |
| `is_test` | TINYINT(1)、NOT NULL、既定値 0 | テストで作った行の印（1）。本番の作成では常に0。画面・API の入力からは付けられない（下の「N-09」）。個人情報ではない |

列名・型は設計案。MySQL のバージョンが JSON 型（5.7 以上）に対応するかは未確認（未決 E）。非対応なら `items` を TEXT に JSON 文字列で入れる。

- 毎回新しい行を作る。同じ選び方でも使い回さない（#29-8）。
- 期限の判定は読み取り時に、アプリ側のサーバー時刻で `現在 − created_at > 720時間（秒で比べる）` なら期限切れ。ちょうど720時間までは有効、1秒でも過ぎたら期限切れ（#30 H）。期限切れなら商品は返さず、期限切れだけを返す（#30 G）。行は消さない。
- 削除はテスト後の後片付けのみ（キックオフ #27）。アプリの機能としての削除は作らない。
- 仕様のデータ表は「30日で期限切れ」、SP-06 は「720時間」と書いている（同じ長さ）。設計では720時間に統一する。

### ブラウザ内保存（お気に入り・カート）

キックオフ #25・#26（OPEN-05）に基づく。サーバーには何も送らない・保存しない。

### コピーボタン（D-08、#32-6）

作成成功の後、リンク（選べる文字として表示）とコピーボタンを出す。

- 押したら `navigator.clipboard.writeText(リンクの全体の URL)` を呼ぶ。
- 成功: ボタンの近くに「コピーしました」を2秒表示して消す。
- 失敗（拒否・クリップボードを使えない環境）: 「コピーできませんでした。リンクを長押ししてコピーしてください」を表示する。消す条件は仕様に書かれていないため、次にボタンを押す（または新しいリンクを作る）まで残す（設計案）。
- どちらの結果でも、リンクは画面に表示されたままで、作成ボタンの状態は変わらない。コピーはサーバーに何も送らない。

### 「選んだ候補」の欄（D-08、#39-3）

- 場所: 検索結果の下。選択が1つ以上あるときに出す（0件のときは出さない。0件のときの出し方は仕様に書かれていません。設計案）。
- 中身: 選んだ順（共有リンクの並びと同じ。#41-7）に、商品名・価格（税込）・理由の文と、「外す」ボタン（#41-5）。選んだ数を表示する。
- **検索し直しても選択を残す**。そのため、画面が持つ選択は商品IDだけでなく、**選んだ時点の商品の表示用の情報**（商品ID・商品名・価格・`category`・`high_rating`・理由の文）を、選んだ順の配列で持つ。再検索で候補の一覧から消えた商品も、この欄に残り、外すまで残る。候補の一覧のカードは、商品IDが選択にあれば「選択中」として表示する（#41-6）。結果一覧で選び直しても外せる（#41-5）。
- 選択の置き場は画面の中だけ（再読込で消える。保存しない）。リンク作成では、商品IDの並びだけを送り（サーバーが作成時点の名前・価格・理由を作り直す。D-05）、欄の表示用の情報は送らない。
- 重複はできない（同じ商品IDは1件。外して選び直した商品は末尾）。
- 10件を超えたら #36 の表示（欄の中の作成ボタンのすぐ上に「共有リンクに入れられるのは10件までです。選ぶ数を減らしてください」を出し、ボタンを押せない）。「外す」で10件以下になれば消える。
- この欄と候補の一覧は同じ選択を見ているので、どちらで外しても同じ状態になる。

### アプリのログ（#39-6）

- 残すのは**時刻・API・結果**だけ。IP アドレスとブラウザの情報（User-Agent など）、入力値（予算・シーン・商品ID）、共有リンクの識別子は残さない（N-13）。
- 形: 1行に、時刻（UTC）、API の種類（`GET /api/candidates` のようにパスの型。識別子の値は入れず `/api/share-links/{id}`）、結果（成功・入力エラー・見つからない・期限切れ・失敗の別と HTTP の状態コード）。
- 実装の方針: サーバーの標準のアクセスログ（IP を出す）は止め（例: uvicorn の `--no-access-log`）、上の形だけを出す自前のログを1か所に置く。例外のときは、種類と場所だけを出し、リクエストの中身・接続情報・秘密情報は出さない。
- 配置（Azure など）の側のログに IP が残るかは、外部公開の承認後に確認する（保留。仕様に書かれていません。未決 M）。

- 共有ページに置かないものは、画面の部品として作らない（購入ボタン・LINE へ送るボタン・延長・再発行・取り消し）。

## 非機能要件の設計（N-03〜N-07、#34）

### N-03 速さ（D-17）

目標（要件 N-03）: 手元の PC から班の DB につないで各10回測り、遅い方から2番目の値（10回を短い順に並べた9番目）で、候補表示2秒以内・共有リンク作成1秒以内・共有ページ表示1秒以内。測り方は N-10（#35 8-3）で決まった。

| 測るもの | 測る場所 | 始点 → 終点 | 目標 | 条件 | 対応する設計 |
| --- | --- | --- | --- | --- | --- |
| 候補表示 | API（`GET /api/candidates`） | リクエストを送る → 応答が返る | 2秒以内 | 予算・送別で上位10件が返る | D-01〜D-04 |
| 候補表示（予算なし）〔案〕 | API（`GET /api/candidates`、`budget` なし） | リクエストを送る → 応答が返る | 2秒以内（案） | 送別だけで上位10件が返る。価格で絞らないので候補が最も多い | D-01〜D-04 |
| 共有リンク作成 | API（`POST /api/share-links`） | リクエストを送る → 応答が返る | 1秒以内 | 商品10件 | D-05 |
| 共有ページ表示 | API（`GET /api/share-links/{id}`） | リクエストを送る → 応答が返る | 1秒以内 | 商品10件のリンク | D-06 |

- 測るのは**アプリの外**（Kurosu の性能テストのコード）。HTTP クライアントで各10回呼んで経過時間を記録する。**1回目も数える**（温め運転で除かない）。画面での表示までの時間は測らない（#35 8-3）。アプリの中に計測用の入口・ログ・環境変数は作らない。
- **予算なしの測定（案、#39）**: 予算なしは価格で絞らないので、候補の数が最も多く、最も重い。性能の測定に入れるかは案（レージ確認）。入れるなら目標は予算ありと同じ2秒。重くなりすぎないよう、送別回数の集計は順位が決まる範囲の商品だけにしている（順位付けの手順6）。
- 測る条件: 手元の PC から班の DB（Azure）へ接続（SSL。N-04）。候補の抽出と送別回数の集計は DB の往復を含む。作成と表示は商品10件で測る。
- **索引案（今は案だけ。足すのはレージ確認後）**: 送別回数の集計（D-04）が遅くて候補表示が2秒を超えたときに限り、注文の側に「商品ID」「推定シーン」「送り先（会社宛てか）」で絞るための複合索引を足すことを検討する。列の実名は未決1のため、ここでは名前を決めない。索引は既存テーブルの変更なので、**足す前にレージに確認する**（#34 7-2）。新しい列は足さない（ADR-003）。測って目標内なら足さない。
- 打ち切り（10秒）は N-03 の目標とは別。10秒は「失敗として扱う上限」（D-12）。

### N-04 DB を守る（D-13）

1. **パラメータ化クエリ**: DB へのすべての問い合わせは、値を「差し込み位置（`%s` など）」に渡す形だけにする。`予算`・`シーン`・商品ID・識別子の値を、f 文字列・`format`・`+` で SQL 文に直接つなげない。`IN (…)` は、件数分の差し込み位置を作り、値は別に渡す。SQL 文を作る部分は `Db`（D-12）に集め、そこでしか DB を呼ばない。
2. **SSL 接続**: DB への通信は SSL。証明書（DigiCert Global Root G2、#28）のファイルの場所は**環境変数で受ける**（名前は設計案 `GIFTIA_DB_SSL_CA`）。パスの値・証明書の実体はコミットしない。接続時は証明書とホスト名を検証し、検証を切る設定は作らない。環境変数が無い・ファイルが読めないときは、接続せず起動に失敗する（500 の詳細にパスを出さない）。
3. **接続情報**: ホスト・DB 名・ユーザー・パスワードも環境変数で受ける（名前は設計案 `GIFTIA_DB_HOST` / `_NAME` / `_USER` / `_PASSWORD`）。`.env` はコミットしない（CLAUDE.md の決まり）。接続情報はまだ保存されていない。
4. **DB アカウントの権限**（設計に書くだけ。作成・設定はしない）:

| 対象 | 与える権限 | 与えない権限 |
| --- | --- | --- |
| 既存テーブル（商品・シーンタグ・注文など） | `SELECT` だけ | `INSERT` / `UPDATE` / `DELETE` / DDL |
| `share_links` | `SELECT`・`INSERT` だけ | `UPDATE` / `DELETE` / DDL（作成後は更新しない。SP-07） |

- アプリは1つの接続アカウントを使う。上の表以外の権限は持たせない。
- 確かめ方（テストの観点）: 既存テーブルへの書き込みが拒否されること、`share_links` の `UPDATE`・`DELETE` が拒否されること、SQL インジェクションを狙った入力（例 `送別' OR '1'='1`）で結果が変わらないこと。

### N-05 表示の安全（D-14）

- 画面に出す文字（商品名・理由・価格・エラー文言）は、React の通常の表示（JSX の `{値}`）だけで出す。React が自動で文字をエスケープする。
- 禁止: `dangerouslySetInnerHTML`、`innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write`。規則として ESLint の `react/no-danger` を error にし、`innerHTML` 系の代入も lint で止める（lint の設定ファイルを置く）。
- API は JSON だけを返す（HTML を返さない）。リンクの `href` に DB の値を入れない（共有リンクは、アプリが自分で作った `/s/{share_id}` だけ）。
- 確かめ方（テストの観点）: 商品名に `<script>` や `<img onerror=…>` を含む固定データを表示して、文字としてそのまま表示され、動かないこと。

### 形式が不正な識別子（D-06、H-14）

`GET /api/share-links/{share_id}` で `share_id` が形式に合わない（22文字でない、使える文字「英大文字・英小文字・数字・`-`・`_`」以外を含む）ときは、**DB を引かずに 404 `not_found`** を返す。422 にはしない。

- 理由1: 形式が不正な場合と、形式は正しいが該当する行が無い場合で応答を分けると、「ここまでは合っている」「識別子の形式はこうだ」と推測する手がかりを与える。同じ 404 にして存在を推測させない（N-02）。
- 理由2: 明らかに不正な値で DB を引かない（無駄な問い合わせと、想定外の文字を DB に渡す機会を減らす。N-04 の補強。値の受け渡しはパラメータ化のまま）。
- 画面の表示は 404 と同じ「リンクが見つかりません」。URL が極端に長い場合も同じ扱い（正規表現に合わない）。
- 確かめ方（テストの観点）: 21文字・23文字・使えない文字（例 `.`・空白・日本語）・空の識別子で、いずれも 404 `not_found` になり、DB への問い合わせが起きないこと。

### N-06 共有リンクの商品数の上限（D-15）

- `POST /api/share-links` の `product_ids` は、**同じ商品IDの重複を1件にまとめた後の件数が1〜10件**。0件は 422 `empty_selection`、11件以上は 422 `too_many_items`。同じ商品IDが重なって届いてもエラーにしない（#36）。
- **重複の除き方と並び（H-23）**: 先頭から順に見て、すでに出た商品IDを捨てる。残った順（**最初に出てきた順**）がそのまま `share_links.items` の並びと、共有ページの表示の並びになる。共有ページの商品は**選んだ順**（#37）に決まった。画面は選択を順序つきの配列で持ち、その順のまま `product_ids` を送るので、「選んだ順」と「最初の出現順」は一致する（API が並べ替えない）。
- **配列の長さの上限（H-23、設計案）**: 重複を除く前の `product_ids` の配列の長さにも上限（`SHARE_REQUEST_MAX_LENGTH` ＝ 50）を置き、超えたら 422 `too_many_items`。画面は重複を作らないので通常は起きない。API に直接、極端に長い配列が届いたときの使いすぎ防止。50は設計案（レージ確認）。
- 画面での選択は上限なしのまま（SP-04）。**11件以上を選んでいる間**は、作成ボタンのすぐ上に「**共有リンクに入れられるのは10件までです。選ぶ数を減らしてください**」を出し、作成ボタンを押せない（#36）。選択数の表示はそのまま。画面は API を呼ぶ前にここで止める。API は 422 `too_many_items` のまま（画面を通らない呼び出しへの二重の防御）。10件以下に減らせば、文言は消えてボタンが押せる。
- 作成回数の制限は、外部公開の承認後に決める（**保留**）。

### N-07 共有ページの公開範囲（D-16）

- **noindex**（H-15）: 共有ページ `/s/[share_id]` に、次の**両方**を付ける。`robots.txt` で止めない（止めると検索エンジンが noindex を読めないため）。
  1. HTTP ヘッダー `X-Robots-Tag: noindex, nofollow`: Next.js の `headers()` 設定で `/s/:path*` のすべての応答に付ける。
  2. `<meta name="robots" content="noindex, nofollow">`: ページの固定の `metadata.robots`（`index: false, follow: false`）。API の結果に左右されず、ページの枠の HTML に常に入る。
- **対象の状態**: 共有ページの4つの状態（**表示・期限切れ・見つからない・失敗**）すべて。状態は同じ `/s/[share_id]` の画面の中で API の結果に応じて切り替わり、ページの枠（上の1・2）は変わらないので、どの状態でも noindex が付く。形式が不正な識別子（H-14）で開いた場合も同じ。
- JSON を返す API（`/api/share-links/…`）の応答にも同じ `X-Robots-Tag` を付ける（JSON が検索に載らないようにする念のため）。
- 確かめ方（テストの観点）: 4つの状態それぞれで、応答ヘッダーに `X-Robots-Tag: noindex` があり、HTML に `meta robots noindex` があること。
- **CORS**: FastAPI の CORS は、許す送信元を**自サイトの画面の送信元だけ**にする（`*` は使わない。認証情報つきの許可も使わない）。許す送信元は環境変数で受ける（名前は設計案 `GIFTIA_ALLOWED_ORIGIN`）。
- 設定は**外部公開の承認後**（公開 URL が決まってから）。承認前の開発中は、画面から API を同じ送信元で呼ぶ（Next.js の `rewrites` で `/api/*` を FastAPI に渡す）ので、CORS を開けない。許可が無いままでも手元で動く。

| アプリ（接続アカウント） | 既存テーブルを `SELECT`、`share_links` を `SELECT`・`INSERT`（N-04） | `UPDATE`・`DELETE`・DDL |
| 管理用アカウント | `share_links` の作成（CREATE TABLE）、行の削除、テーブルの削除（DROP TABLE） | アプリからは使わない。アプリの環境変数・リポジトリに入れない |
| レージ | 管理用アカウントで、上の作業を手で行う | — |
| Terao | 管理用アカウントでの手順書（作成・テストの行の確認と削除・テーブルの削除・戻し）を書く | 管理用アカウントの値を文書・コードに書く |
| Kurosu | テストで行を作り、終わったら印の付いた行だけが消えたことを確かめて `evidence/` に残す | 管理用アカウントを持つ |
| Takahiro（設計） | 列・印・権限・戻し方の設計を書く | アカウントの作成・権限の設定・DB への接続 |

**テスト用の印（`is_test`）**

- `share_links` に列 `is_test`（TINYINT(1)、NOT NULL、既定値 0）を持たせる。通常の作成は印なし（0）。
- 印を付けられるのは**テストのコードからだけ**。共有リンクを保存する部品（`Db` を通す保存処理）に、印を決める依存（既定は「印なし」）を置き、テストでだけ「印あり」に差し替える（D-11・D-12 と同じ方法。`dependency_overrides`）。リクエストの本文・クエリ・ヘッダー・環境変数・画面からは付けられない。
- 期限切れを作るための「31日前」の行も、テストの `Clock`（D-11）と印を使い、アプリの `INSERT` で作る（管理用アカウントを使わない）。
- 印の付いた行の消し方（管理用アカウント、手順は Terao）: 先に `SELECT … WHERE is_test = 1` で件数と中身を確認し、そのあと `DELETE … WHERE is_test = 1`。印の無い行は消さない。
- 印の列が無いと「テストの行」と「本物の行」を区別できないため、列で持つ。個人情報は入れない（N-13）。

**戻し方**

| 失敗 | 戻し方 |
| --- | --- |
| アプリの不具合 | 前のコミットに戻して入れ直す。公開中（承認後）は、先に公開を止める |
| DB（`share_links`） | 管理用アカウントで `share_links` を DROP すれば元どおり（既存テーブルは変えていない。ADR-003） |
| テストで作った行 | 管理用アカウントで、印（`is_test = 1`）の付いた行だけを消す |

### N-12 使いやすさ（D-22）

- **押す場所の大きさ**: ボタン・リンク・入力欄・選択の部品は、縦横44px以上（最小サイズを1つの値 `--tap-min: 44px` にして全体で使う）。
- **色の差**: 文字と背景の色は WCAG AA（通常の文字 4.5:1、大きい文字と部品の枠 3:1）。色は画面の設定の1か所（色の変数）に集め、自動検査（axe など）で確かめる。
- **キーボード**: 主要な流れ（予算・シーンの入力 → 候補を出す → 選ぶ → リンクを作る → コピー）が、キーボードだけで進める。Tab で見た目の順に進み、フォーカスの枠が見える。ボタンは Enter・Space で押せる。選択の部品は、キーボードで選ぶ・外せる。キーボードから抜けられなくなる場所を作らない。
- **操作回数の数え方（9回以内、#38）**: 数えるのは「入力欄に入れる（文字数に関わらず1回）」「ボタンを押す・部品を選ぶ（1回）」。スクロール、欄の間の移動（Tab・フォーカス）、確認のための目視は数えない。候補を3つ選ぶ場合:

| 回 | 操作 |
| --- | --- |
| 1 | 予算欄に入れる |
| 2 | シーン「送別」のボタンを押す |
| 3 | 「候補を出す」を押す |
| 4〜6 | 候補を3つ選ぶ（1つ1回） |
| 7 | 「共有リンクを作る」を押す |
| 8 | 「コピー」を押す |

- 候補を3つ選ぶ場合は上の8回で、**余裕は1回**（9回以内）。予算は任意なので、入れないときは7回。確認の画面や追加の操作（作成後の「リンクを表示する」ボタンなど）を足さない。作成に成功したら、リンクとコピーボタンは自動で表示する（#30 K）。

## テストのための差し替え

目的: 720時間の判定（U-15・I-18）とサーバー側の10秒打ち切り（E-13）を、実際に待たずに確かめる。差し替えは**テストのコードからだけ**行う。公開する API・環境変数・画面・設定ファイルに入口を作らない（本番の動作を外から変えられないため）。

### D-11 時刻の差し替え

- 期限判定と `created_at` の記録は、`datetime.now()` を直接呼ばず、`Clock`（`now()` を持つ小さな部品）から現在時刻を受け取る。`Clock` は FastAPI の依存（`Depends`）として注入する。
- 本番の `Clock` は、アプリのサーバー時刻（UTC）を返す。
- 期限判定の関数は `is_expired(created_at, now)` の形で、`now` を引数に取る純粋な関数にする（DB も時計も使わない）。単体テストはこの関数を直接呼び、`created_at` と `now` の差を秒で与える。
- 結合テストは、テストのコードの中で FastAPI の `app.dependency_overrides` に固定の `Clock` を入れる。これはテストのコードからだけ使い、アプリの起動時の設定や環境変数からは読まない。
- 確かめられること:

| 確認 | 作り方 |
| --- | --- |
| 720時間ちょうどは有効 | `now − created_at ＝ 720×3600 秒` に固定 |
| 1秒過ぎたら期限切れ | `now − created_at ＝ 720×3600＋1 秒` に固定 |
| 作成から31日前の行（#27） | `created_at` を直接入れたテスト用の行を作り、`now` は現在に固定 |

### D-12 DB 問い合わせの遅れの差し替え

- DB の問い合わせは `Db`（実行口）を通す。`Db` は問い合わせに10秒の上限を掛け、超えたら打ち切って 500 `internal_error`（D-01・D-05・D-06 共通、入力検証表）にする。上限の10秒は `Db` の中の定数で、外から変えられない。
- 結合テストは、テストのコードの中で `app.dependency_overrides` に「問い合わせの前に待ちを入れる `Db`」を入れる。待ちは時計に頼らず `asyncio.sleep(11)` を使い、11秒の遅れを作る。時計の固定（D-11）とは別の部品なので、組み合わせて使える。
- 確かめられること: 11秒かかる問い合わせは約10秒で打ち切られ、候補取得・共有リンク作成・共有リンク表示のいずれも500を返す。作成の場合は、打ち切り後にサーバー側で行が作られても許す（#30 C）。
- 画面側の10秒（#29-14）は、画面の定数 `REQUEST_TIMEOUT_MS ＝ 10000` と `AbortController` で実装する。画面のテストは偽の時計（テスト用タイマー）で10秒を進める。この定数はテストの設定で変えられない。

### 入口を作らないことの確認

- 差し替えの手段は、テストのコード内の `dependency_overrides` と、テスト用の偽タイマーだけ。環境変数・クエリ・ヘッダー・管理用の画面や API は作らない。
- 本番の起動コードは `Clock`・`Db` の本番版だけを登録する。テスト用の版（固定の時計・遅れ付きの `Db`）はテストのフォルダに置き、本番のコードから読み込まない。
