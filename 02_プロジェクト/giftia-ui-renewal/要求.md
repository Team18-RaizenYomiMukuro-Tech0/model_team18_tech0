# 要求 — Giftia UI/UX リニューアル

中心の問い:

> ギフトを探す人が、条件で絞って比較し、1つに決めるまでを、迷わずに進められるか？

（決定者: レージ、2026-11-07、`inputs/キックオフ記録.md` #3）

## 判断と保留

- 関連ADR: ADR-001（成功の定義）
- 保留（PDF から引き継ぎ。確認者はレージ。キックオフ記録 #5 により、すべて決めてから実装計画に進む）
  - OPEN-01: 決定（#24）。案A（淡色）、PC 幅 1280px、スマホ幅 375px
  - OPEN-02: 決定（#25）。各条件は単一選択、条件間 AND。お礼・誕生日・送別は同名タグ、取引先へのお礼も「お礼」タグ（取引先へのお礼は #50-6 で取り消し。シーンはお礼・誕生日・送別の3つ）
  - OPEN-03: 決定（#24）。「〜2,999円／3,000〜4,999円／5,000円〜」、税込
  - OPEN-04: 決定（#25）。キーワードは Enter か検索ボタンで確定。クリアはキーワード以外。12件ずつページ送り、おすすめ順。ただし「Enter か検索ボタンで確定」は、ヘッダーの検索（「準備中」。#41-8）に係るため今回は作らない（#46-7）
  - OPEN-05: 一部決定（#25）。お気に入りはブラウザ内保存。カートはブラウザ内保存で、追加・数量変更・削除・合計（同一商品は数量+1）。「注文へ進む」はボタンだけ（#26）。ログインは本番に作らず、入口は「準備中」のまま（運営の回答 #65。手元の試作は別で、本番の評価に入れない。ADR-005）
  - OPEN-06: 一部決定（#24）。欠けた項目は表示しない（値を作らない）。画像はカテゴリー共通イラストに「イメージ」と表記。未分類はカテゴリー絞り込みで出さない（キーワードでは出す）。共有リンクの削除商品は「この商品は販売終了しました」、在庫0は「在庫なし」（#25）
- 食い違い（要件の段で決める）
  - 技術条件: ケースはフロントエンド Next.js・バックエンド FastAPI を指定。PDF は FastAPI・Azure のみ記載
  - ケース必須の流れ（入力 → DB から複数候補 → チームのロジックで順位付け → 返す）が PDF に無い
  - 画面イメージ案 A の評価 4.5 の商品に高評価バッジが無い（RAT-02 と矛盾。文書を優先）
