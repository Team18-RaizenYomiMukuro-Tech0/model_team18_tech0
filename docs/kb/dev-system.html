1考え方：AI の出来はぶれる。そのぶれを仕組みで抑える5分

要点
  • AI は同じ頼み方でも、出来が毎回少しぶれる。
  • だから「うまく頼む」より「ぶれても大丈夫な仕組み」を先に作る。
  • 仕組みは2つ。決まりを文書に書いて毎回読ませる／書く役と確かめる役を分ける。

このプロジェクトの背骨は一文で言える。「正しく進む確率を、仕組みで上げる」。

仕組みの1つ目は、決まりを .md に書いて毎回読ませること。たとえば CLAUDE.md には「文書に書いていないことは作らず、『仕様に書かれていません』と報告して止まる」と書いてある。AI スタッフは、書かれていないことを想像で補わない。ぶれる幅が狭くなる。

2つ目は、1体が書いて、別の1体が確かめること。2体とも同じところを見落としたときだけ、ミスが残る。前回の実例では、書記の下書きをテスト役が事実確認し、公開前に「必須の修正2件・推奨3件・任意2件」が出た。必須の2件を直してから公開した。効いたのは、確かめる役に元の記録を見に行かせたこと。同じモデルに同じ前提で見せるだけだと、ミスが重なることがある。

体制は、人間3名（GitHub Org メンバー: PM・re-ji・matsuki）と AI スタッフ6名。人が決め、AI が提案・実装・確認する。

35文書：壁打ちで作る、HTML 化、モック8分

要点
  • 5文書は、りじちょーの一問一答で人が育てる。AI が全欄を代筆した回答は本人の証拠にならない。
  • 5文書は HTML になってハブから開ける動いている。
  • 画面が関わる迷いどころは、モックを見て人が選ぶ試行。

壁打ち。 りじちょーは「○○はどうしますか」と一問ずつ聞く。選択肢は提案するが、決めるのは人。「Aで」「決定」と言われたら文書の「決定事項」に書き戻す。「どっちも」「たぶん」は決定にならない。個人回答の原文は上書きしない。

HTML 化動いている。 書くのは今までどおり .md だけ。ビルド時に HTML にして GitHub Pages に公開する。ID（R・F・N・SP など）は文書間のリンクになる。ハブの「5文書」欄から開ける。案件フォルダが決まるまでは _template が表示される。

モック試行。 画面が関わる仕様で、人が迷っている論点だけが対象。それ以外は従来どおり文書で決める。

段階モックの形
要件紙芝居 3〜5 枚でよい
仕様クリックで動くモック。各画面に SP 番号

案A・案B のモックを見比べ、本人回答（例「Aで」）を記録して確定する。置き場は docs/mock/、決めたことはハブの「🙋 決めること・決めたこと」欄。W2 の終わりに見直す試行ルール。背景は、前回の開発で完成形が見えず、AI の案どおりにしか進まなかったこと。

4Issue の管理：テンプレートと、完了条件の具体化8分

要点
  • Issue は「これは何？」「完成すると何ができる？」「完了条件の表」の順で書く。
  • 完了条件は1行に確認1つ。テストか画面のどちらかで、AI も人も ○/× を付けられる形にする。
  • 前回は記号だけの Issue で何を作るか分からなかった。今回はそこを直した。

Issue テンプレート（.github/ISSUE_TEMPLATE/task.md）の節は次のとおり。

節役割
💬 これは何？作るものを1行で
✅ 完成すると何ができる？使う人から見た変化。各行の末尾に完了条件の番号
🔗 対応する文書の IDどの要件・仕様・テストの話か
⛓️ 依存先に閉じている必要がある Issue
📁 触るファイルここに無いファイルを触るなら PM に確認
🎯 完了条件表。1行＝1つの確認
任せてよい範囲自分で決めてよいことと、PM に確認が要ること
🚫 やらないこと範囲が広がるのを防ぐ

完了条件の書き方（判定できる5条件）： 1行に確認は1つ／確認の種類が決まっている（テストか画面）／誰がやっても同じ手順／合格の基準が値か表示で書かれている／証拠の形が決まっている。

前と後

前（前回）
  • Issue の書き出し　「対応: SP-53〜SP-57」「受入基準」「触るファイル」。記号と番号が中心で、文書を開かないと中身が分からない
  • 完了条件　初心者に分かる言葉になっていない
  • 裁量　自分で決めてよいことの線引きがない
  • PR 側　証拠の置き場が決まっていない
後（今回）
  • Issue の書き出し　先頭に「何を作るか」「できると何ができるか」を普通の言葉で書く
  • 完了条件　テストか画面で1行ずつ ○/× を付けられる形。悪い例「全関数を実装する」は、何をしたら合格か決まっていない
  • 裁量　「自分で決めてよいこと」と「PM に確認が要ること」を Issue ごとに書く（例：関数名やエラー文言は自分、画面項目の追加や完了条件の変更は PM）
  • PR 側　PR テンプレートに「完了条件ごとの証拠」の表。テストはコマンドと出力、画面はスクリーンショット

注意：Issue の大きさの目安（1〜2日、完了条件3〜7行、触るファイル5つ前後）は案で、PM の確認待ち。

6レビュー：PR レビュー規定、AI レビューの自動化、複数エージェント8分

要点
  • AI レビューは完了条件を1行ずつ判定する。承認できるのは条件がそろった PR だけ。
  • ルール・5文書・秘匿情報にかかわる変更は、AI は承認せず人に回す（needs-human）。
  • AI レビューの自動実行は作ってあるが、本番稼働は未確認【M80-8】。複数エージェントでのレビューは予定。

AI レビューの流れ動いている：規定と指示文／起動の自動化は未確認

  1. 未レビューの PR を探す。

  2. 自分の PR は飛ばす（本人は承認できない）。

  3. 完了条件の表を1行ずつ判定し、コメントに ○／×／確認できない を書く。

  4. 条件がそろえば ai-approved。足りなければ承認せず、足りないものをコメントする。

起動は、Draft でない PR を作ったときと、毎朝 8:00（JST）。Draft の間は起動しない。作業中の PR は Draft で出す。

AI が承認しない条件

  • Issue が紐づかない PR（判定する完了条件が0行になるため）。
  • 5文書を変える／変える必要があるのに変えていない。
  • PM に確認すべき内容（I/F 契約の変更、受入基準の変更、新しい外部サービス、スコープの増減）。
  • ルールそのものを変える（CLAUDE.md、00_ルール/ ほか）。
  • 秘匿情報の疑い。

これらは needs-human になり、人が見る。AI の承認は、その Claude を動かしている人の名前で記録される。「重要な変更は人が見る」は設定では強制できず、規定で守っている。

マージの権限：ai-approved が付いた PR は作成者がマージしてよい。ダッシュボード、01_ナレッジ/ など開発に影響しない作業は自分でマージしてよい。needs-human の PR は他のメンバーの承認を待つ。

  • 失敗の多くは「確認前に動いた」「境界が書かれていなかった」「書式がそろっていない」。
  • 迷ったら止まって聞く。書かれていないことは作らない。
  • 完了報告には証拠を付ける。
ハマりどころ
型起きること対処
確認前に動く「待って」の前に作り始め、作り直しになる決定（「Aで」「OK、進めて」）が出るまで発注しない
境界が書かれていない同じ場所を別の書き方で作って衝突する触るファイルを Issue に書く。無いファイルを触るときは PM に確認
件数・番号の取り違え依頼文の件数が実際と違う一覧を作ってから数える。並べ替えたら番号参照を検索し直す
PR 本文の取り違え別の下書きを PR 本文にしてしまった本文ファイルは新しい名前で、固定の場所に置く
担当と実装者の取り違えAssignee を「書いた人」と思い込む誰が書いたかは git log --diff-filter=A -- &lt;ファイル&gt; で確かめる
体制・人数のゆれ文書によって人数や役割が違う本人に確認して1か所を正とし、他を合わせる（人数は3名に統一済み）
