ねらい作った企画書・仕様書を、りじちょーと壁打ちしながら5文書に育てる。抜けている点を明確にするのにも使える。

仕組み

  4. 画面が絡む迷いは、モックを見て選ぶ試行。置き場 docs/mock/。W2 の終わりに見直す。

4Issue7分

ねらいIssue を「作業内容と完了条件が、人にも AI にも判定できる形」にする。

仕組み

  • 書き方は .github/ISSUE_TEMPLATE/task.md で制御している。テンプレートの節を埋めると、決めたい形になる。規定は 00_ルール/Issue作成規定.md。
  • 節ごとの、ねらい：
節ねらい
💬 これは何？作るものを1行で。専門用語だけで書かない
✅ 完成すると何ができる？使う人から見た変化。各行の末尾に完了条件の番号。表に無い変化は書かない
🔗 対応する文書の ID5文書のどの ID の話かをつなぐ
⛓️ 依存先に閉じている Issue。着手前に確認
📁 触るファイル範囲を決める。無いファイルを触るときは PM に確認
🧬 起因設計変更のときだけ。元 PR と変えた ID。ラベル design-change
🎯 完了条件表。1行＝1つの確認（テストか画面）。手順・合格の基準・証拠の形まで書く。1行ずつ ○/× を付けられる
任せてよい範囲自分で決めてよいこと／PM に確認が要ること
🚫 やらないこと範囲が広がるのを防ぐ
👀 Reviewer／👤 担当・期限誰が見るか、誰がいつまで（PM が決める）

6AI レビュー6分

ねらいレビュアーの負担を減らし、開発のスピードを上げる。AI が先に見て、人は重要なものだけ見る。

仕組み

  • 規定：00_ルール/PRレビュー規定.md。AI は完了条件の表を1行ずつ判定し、○／×／確認できない を書く。そろえば ai-approved。
  • AI が承認せず人に回す（needs-human）：Issue が紐づかない PR／5文書の変更／PM に確認すべき内容／CLAUDE.md・00_ルール/ などルールの変更／秘匿情報の疑い。
  • 起動は Draft でない PR を作ったときと、毎朝 8:00（JST）。作業中の PR は Draft で出す。
  • マージ：ai-approved が付いたら作成者がマージしてよい。needs-human は他のメンバーの承認を待つ。

動いている要設定

自動レビューにはセットアップが必要。 手順は docs/setup.html 付録1のオプション（AI レビューの定期実行）と 01_ナレッジ/レビュールーチンの設定手順.md。設定しないと自動では動かない。

あなたがやること

  • PR には Issue を紐づけ、完了条件ごとの証拠（テストは出力、画面はスクリーンショット）を貼る。
  • 自動レビューを使うなら、セットアップ（付録1のオプション）を済ませる。

状態規定・機械チェック動いている／AI レビューの自動起動動いている（試験 PR で PR 作成の2秒後に起動を確認。自分の分は docs/setup.html 付録1で設定。ラベル・承認の付与は未確認）／複数エージェントのレビューは予定
