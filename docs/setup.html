3Munder Difflin を入れる5分

要点

  • 初回起動はブラウザでサインインする。

Munder Difflin は、Claude Code などのコーディング AI を「チーム」として自分の PC で動かすデスクトップアプリ。AI 自体は含まれず、入れた AI を動かす。

  1. 入手する。

    munderdiffl.in から 0.5.7 を入れる（2026-10-27 時点の最新。PM の Mac で起動確認済み）。GitHub Releases には載っていない。Windows 版の起動は未確認。

  2. 初回起動。

    最初の画面で「On my own / With my team」を選び、ブラウザでサインインする。コードが進まないときは「Code from the browser」にコードを貼り、「Use this code」を押す。続いて「Name your workspace」が出る（既定は HarnessAgents）。

  3. 購入画面。

    「Continue with the free version / I have a licence key / Get PRO」が出る。チームの現行ガイドは無料版で可としている。Pro の無料期間（2026-10-24 まで）は終了済み。

  4. Claude Code が入っていないとき。

    エージェントの端末にカードが出る。Install を押すと入る。サインインはアプリ内（0.5.3 以降。公式 README の記述を現行ガイド経由で記載、今回は再確認していない）。

  5. ワークスペースの場所。

    Browse で選ぶ。ここで選ぶのは章2でクローンしたフォルダ（model_team18_tech0）。各エージェントは与えられたフォルダから始まるが、そこに閉じ込められるわけではない。

4Munder Difflin の基本7分

要点
  • 画面でスタッフにメッセージを書いて頼む。クリックすると端末の様子が見える。
  • 返事は Inbox、作業の一覧は Tasks、人にしか進められないことは ASK ME に出る。
  • 予算とブレーカーがあり、使いすぎや繰り返しを止める。

まず用語を一言ずつ。

用語意味
agent（エージェント）ファイルを読み・書き・コマンドを実行する、続けて動く AI メンバー。このプロジェクトでは「スタッフ」
orchestrator（まとめ役、呼び名 god）人が直接話す相手。他のエージェントへの依頼を取りまとめる
temp（一時エージェント）1つの仕事のためだけに作られ、終わると報告して消える。temp は temp を作れない
hive（ハイブ）エージェントが共有する、ファイルだけでできた作業場。記憶・受信箱・ボード・ログ

操作

やりたいこと操作注
頼むメッセージ欄に、成果・フォルダ・完了の条件を書くエージェントをクリックすると端末の様子が見える

定期実行Automations（Pro）／Triggers（無料版の画面）。タイマーや webhook で仕事を送る保存してオンにすると即時有効

board は2つある。

  1. hive/board.md：自由記述の計画書。書き手はまとめ役（god）だけ。

ブレーカー。 同じ動作の繰り返し、エラーの連発、使いすぎを見張り、段階的に止める。steer（促す）→ constrain（読み取りのみ）→ stop（停止）。「Circuit breaker: steer」のようなメッセージが来たら、同じことを繰り返さず、試したことをまとめて指示に従う。

6動作確認：Issue を1つ作り、PR まで一周する5分

要点
  • 練習用でよい。Issue → ブランチ → PR → 機械チェック、まで一周する。
  • PR は Draft で出し、レビューしてほしくなったら Draft を解除する。
  • 終わったら、結果を ○/× だけで GitHub の Issue に返す。
  1. Issue を作る。

    .github/ISSUE_TEMPLATE/task.md の形で、「これは何？」「完了条件の表」を書く。完了条件は、テストか画面で1行ずつ判定できる形（例：ある文書に1行追加し、git diff に追加行が出る、など）。

  2. ブランチを切る。

    main から作業用のブランチを作る。

git switch -c docs/practice-<自分の名前>
  1. 変更して push する。

    変更したファイルだけを git add に指定する（git add -A は使わない）。

  2. PR を出す。

    PR テンプレートの各節を埋める。「対応する文書の ID」「対応する Issue（Closes #番号）」「完了条件ごとの証拠」「チェック欄」。Draft で出す。

  3. 機械チェックを見る。

    テンプレート記入のチェックが pass するか確認する。足りなければ PR のコメントに理由が出る。

  4. 結果を返す。

    ○/×だけを、Issue 導入確認: &lt;GitHub名&gt; (&lt;OS&gt;) として1つ作って貼る。ログ全文と、ユーザー名の入ったパスは貼らない。

ハマりどころ
  • Issue のない PR は、AI レビューが承認しない。練習でも Issue を作る。
  • PR 本文のファイルは、他の下書きと混ざらない名前で作る。
