# セッション Cookie 方式と JWT 方式の違い（#136 の試作で確かめたこと）

試作: `experiments/login/app.py`（手元の SQLite・bcrypt・FastAPI）。本番には入れない（ADR-005）。
JWT（JSON Web Token）は、ログインした人の情報と期限を入れて署名した文字列。

| 観点 | セッション Cookie 方式 | JWT 方式 |
| --- | --- | --- |
| 状態を持つ場所 | **サーバー**（`sessions` 表）。Cookie には乱数の ID だけ | **トークンの中**（署名つき）。サーバーは覚えない |
| 送り方 | ブラウザーが Cookie を自動で付ける（`HttpOnly`・`SameSite=Lax`） | 呼び出し側が `Authorization: Bearer …` を付ける |
| 取り消し | **すぐできる**（行を消す。試作の logout で確認） | **期限まで取り消せない**（`test_c3_jwt_logout_cannot_revoke`）。止めるには拒否リストなど、結局サーバーの状態が要る |
| 期限 | サーバー側の `expires_at`。延ばす・縮めるも後から可能 | トークン内の `exp`。発行後は変えられない（短くして更新用を足すのが定石） |
| 1 回あたりの確認 | 毎回 DB を 1 回引く | 署名の検査だけ。DB 不要（台数が増えても共有しやすい） |
| 盗まれたとき | ID を無効にして終わり | 期限まで使われる。短い期限が前提 |
| 主な弱点 | CSRF（別サイトから勝手に送らせる）。`SameSite` で下げる | XSS でトークンが抜かれる（画面側に置くとき）。署名の鍵が漏れると全員なりすまし可 |
| 向く場面 | 画面とサーバーが同じサイトのアプリ | 画面とサーバーが別・複数サービス・スマホアプリ |

## 試作で確かめたこと（`pytest` で再現できる）
- パスワードは bcrypt（`$2b$` 始まり）。平文は列に残らない（完了条件 1）。
- どちらの方式も、正しいパスワードのときだけ保護された API が見える。間違いは 401（2・3）。
- セッションは logout の直後に見えなくなる。JWT は logout の相手にならず、期限切れで初めて 401 になる（3）。
- JWT の検査は `algorithms=["HS256"]` に固定し、`exp`・`sub` を必須にした（`alg=none` を許さない）。

## 試作の限界（作らなかったもの）
本番の `secure` Cookie、CSRF 対策、ログイン失敗の回数制限、JWT の更新・拒否リスト、パスワード変更。この試作は仕組みの違いを確かめるためだけのもの。
