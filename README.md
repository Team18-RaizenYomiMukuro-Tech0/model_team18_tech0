# Giftia UI/UX リニューアル

贈り物を選ぶ人が、シーンや相手から候補を探し、理由つきのおすすめを見て、共有リンクで相談できるようにする Web アプリです（ケース課題「Giftia UI/UX リニューアル」。架空データだけを使います）。

このリポジトリには、アプリのコード（`frontend/`・`backend/`）と、それを作るための文書（要求・要件・仕様・設計・テスト設計）が一緒に入っています。AIスタッフ（りじちょー＋5名）と進めるグループ開発の基礎ファイル一式でもあります。

## フォルダの役割

一番上のフォルダだけを並べます。

| フォルダ | 言語 | 役割 |
| --- | --- | --- |
| `frontend/` | TypeScript | 画面（Next.js）。本番は App Service で動く。 |
| `backend/` | Python | API（FastAPI）。本番は Azure Functions で動く。`function_app.py` が `main.app` を包む。 |
| `02_プロジェクト/` | 文書 | この案件の 5 文書・ADR・実装計画・Issue の下書き。入口は `02_プロジェクト/giftia-ui-renewal/`。 |
| `00_ルール/` | 文書 | 作業ルール・開発フロー・PR レビュー規定・Issue 作成規定。 |
| `01_ナレッジ/` | 文書 | 決定と学びの記録、失敗の型（`mistakes/`）、定期実行の導入手順。 |
| `docs/` | HTML・PDF | 案内は `docs/README.md`。開発ハブ・セットアップガイド・モック・図・ケースの要件 PDF。 |
| `evidence/` | 画像・文書 | 全体で使う証拠（Issue・PR ごとの画面確認など）。 |
| `scripts/` | Python・シェル | 開発の補助（hooks、週1要約、進捗の集計など）。アプリのコードではない。 |
| `munder/` | JSON・文書 | AIスタッフの定義とキャラ対応表、参加者の名前の対応。 |

`.claude/` はスタッフの定義、`.githooks/` は秘密情報の混入を止めるフック、`.github/` は PR・Issue のテンプレートと CI です。

### 似た名前の置き場の違い

- **`munder/`**: AIスタッフ（りじちょーなど）の定義とキャラ対応表で、アプリとは関係がない。
- **`docs/`**: 開発ハブ・モック・ケース PDF など、人が読む資料の置き場。
- **`evidence/`（ルート）**: Issue・PR ごとの動作確認の画像（`240-impl/`、`like7-reach/` など）。
- **`02_プロジェクト/giftia-ui-renewal/evidence/`**: 受入基準 A-01〜A-12 の独立評価と、R-01 列の画面幅ごとの測定など、5 文書の評価に使う証拠。

## なぜ画面と API で言語が違うのか

画面は TypeScript（Next.js）、API は Python（FastAPI）に分けています。分けた理由は、**ケース課題の技術条件でフロントエンドは Next.js、バックエンドは FastAPI と指定されているためです**。

- 根拠: `02_プロジェクト/giftia-ui-renewal/要件.md` の技術条件（ケース Exhibit 5）、`要求.md` の「食い違い（要件の段で決める）」の技術条件、`設計.md` 冒頭の技術条件、`ADR.md` ADR-004。
- 順位付けと理由の生成は FastAPI（Python）で行い、SQL では候補の抽出と回数の集計だけをします（`設計.md`「順位付けと理由の生成は FastAPI（Python）で行い」の節）。

指定を超えて「なぜ TypeScript と Python の組み合わせが良いか」を述べた文書は、5 文書・ADR の中に見つかりませんでした。ここでは書きません。

## 手元で動かす

画面と API を別々に起動します。必要なもの: Python 3、Node.js、チームの DB 接続情報（`backend/.env` に書く。値はコミットしない）。

1. API を起動します（8000 番）。

   ```bash
   cd backend
   python3 -m venv .venv && source .venv/bin/activate
   pip install -r requirements.txt
   cp .env.example .env          # 接続情報を自分で書く。.env はコミットしない
   uvicorn main:app --port 8000
   ```

2. 別の端末で画面を起動します（3000 番）。開発中は `/api` が自動で `http://127.0.0.1:8000` に転送されます。

   ```bash
   cd frontend
   npm install
   npm run dev
   ```

3. ブラウザで `http://localhost:3000` を開きます。

テスト・静的検査は次のとおりです。API 側の詳しい手順は `backend/README.md` にあります。

```bash
cd backend && pip install -r requirements-dev.txt && pytest -q && ruff check . && mypy .
cd frontend && npm run lint && npm run typecheck && npm test
```

DB を読むテスト（`test_*_db.py`）は、`backend/.env` が無いと飛ばされます。

## 本番の構成

| 部分 | 置き場所 | 中身 |
| --- | --- | --- |
| 画面 | Azure App Service（Node 24） | `frontend/`（Next.js） |
| API | Azure Functions（Flex 従量課金・Python 3.14） | `backend/`（FastAPI を `function_app.py` で包む） |
| DB | ケース提供の MySQL | 班の DB（架空データ） |

画面と API は別のホストです。画面のビルド時に `NEXT_PUBLIC_API_BASE` で API の場所を渡します。置き場所は講師が用意したリソースです（`ADR.md` ADR-004 の 2026-11-11 の追記、`設計.md` D-33）。URL と接続情報はここに書きません。

## 5文書の入口

入口は `02_プロジェクト/giftia-ui-renewal/` です。要求 → 要件 → 仕様 → 設計 → テスト設計の順に読みます。

| 文書 | ファイル | 何が書いてあるか |
| --- | --- | --- |
| 要求 | `要求.md` | 誰の何を解決するか |
| 要件 | `要件.md` | 機能（F）・非機能（N）の要件 |
| 仕様 | `仕様.md` | 画面と API の振る舞い（SP） |
| 設計 | `設計.md` | 構成・データ・処理の流れ（D） |
| テスト設計 | `テスト設計.md` | 単体・結合・システムのテスト（U・I・S・NF） |

あわせて、決定の記録は `ADR.md`、いまの段は `IMPLEMENTATION_PLAN.md`、テストの実行は `テスト実行手順書.md` を見ます。進め方（V字）の正本は `00_ルール/開発フロー.md` です。

## ディレクトリの分け方（仕様駆動）

文書とコードを同じリポジトリに置き、文書を正本にして作ります。分け方の根拠は次のとおりです。

- **5文書は案件フォルダにまとめる**: `02_プロジェクト/<案件>/` に要求・要件・仕様・設計・テスト設計を置きます。PR の重さを決める規定も、このパスを「5文書を変えている」の判定に使っています（`00_ルール/PRレビュー規定.md` §4、`00_ルール/Issue作成規定.md`）。
- **文書を先に承認してからコードを作る**: 5文書のコミット ID を示し、PM が「OK、進めて」と言ってから実装します（`00_ルール/作業ルール.md` §1、`00_ルール/開発フロー.md` §3 の段6）。コードは文書の ID（F・N・SP・D）に対応づけます。
- **ルール・ナレッジ・案件を分ける**: 毎回守るルールは `00_ルール/`、学びは `01_ナレッジ/`、案件ごとの文書は `02_プロジェクト/` です。番号は読む順番です（`CLAUDE.md`）。
- **モックと図は `docs/mock/` に置く**: 原本をリポジトリに置き、GitHub Pages で全員が同じリンクで開けるようにします（`00_ルール/開発フロー.md` §6）。
- **テストの証拠は `evidence/` に残す**: 各段の通過は証拠のパスを残します（`00_ルール/開発フロー.md` §4）。

「なぜこの番号と名前の並びにしたか」を直接書いた文書は、5文書・ADR・`00_ルール/` に見つかりませんでした。上の項目は、規定が実際にこの置き場を前提にしている箇所だけを挙げています。

## 始め方
1. クローンしたら、秘密情報の混入を止めるフックを有効にする（各自1回）。
   ```bash
   git config core.hooksPath .githooks
   ```
2. `CLAUDE.md` と `00_ルール/開発フロー.md` を読む。
3. PR のレビューとマージの決まりは `00_ルール/PRレビュー規定.md`。
4. 週1要約の定期実行・失敗の自動吸い上げを入れる（任意）。OS に合わせて、Mac は `01_ナレッジ/定期実行の導入手順.md`、Windows は `01_ナレッジ/定期実行の導入手順_Windows.md`。
