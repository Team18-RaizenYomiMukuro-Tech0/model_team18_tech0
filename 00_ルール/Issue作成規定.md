# Issue作成規定

Issue の書き方の決まり。実装経験が浅い人でも、Issue だけ読めば迷わず実装でき、レビューする人（と AI レビュー）が完了条件を1行ずつ「合格／不合格」で判定できる状態にする。

- Issue の型は `.github/ISSUE_TEMPLATE/task.md`。各節に記入例がある。
- PR 側の対応は `.github/pull_request_template.md`、レビュー側の対応は `00_ルール/PRレビュー規定.md` §4。
- 5文書（`02_プロジェクト/*/`）の ID に対応づける。文書に書いていないことは Issue にも補って書かない（食い違いに気づいたら PM に確認する）。

> 状態: §3「Issue の大きさの目安」と §4「仕様変更で増えたタスクの起票ルール」は**案**。PM の確認が取れるまでは、運用しながら直す前提で使う。

## 1. Issue に書くこと（節の役割）
| 節 | 役割 |
| --- | --- |
| 目的 | 何のための作業かを、専門用語に頼らず 1〜3 行で |
| 対応する文書の ID | どの要件・仕様・テストの話か |
| 依存 | 先に閉じている必要がある Issue（なければ「なし」） |
| 触るファイル | 変更・追加するパス。ここに無いファイルを触る必要が出たら PM に確認 |
| 完了条件 | 表。1行=1つの確認（§2） |
| 任せてよい範囲 | 自分で決めてよいことと、PM に確認が要ること（§5） |
| やらないこと | 範囲が広がるのを防ぐ |
| 実装のヒント | 任意 |
| 担当・期限 | 担当者、期限（週・マイルストーン） |

## 2. 完了条件の書き方

### 2-1. 判定できる書き方の条件
完了条件の各行は、次の5つをすべて満たす。

1. **1行に確認は1つだけ**。「A と B ができる」は2行に分ける。
2. **確認の種類が決まっている**。`テスト`（コマンドで機械的に確かめる）か `画面`（画面を操作して目で確かめる）。
3. **誰がやっても同じ手順になる**。コマンドそのもの、または画面で押す・入力するものを順に書く。
4. **合格の基準が「値」か「表示」で書かれている**。「正しく動く」「適切に表示される」のような感想は基準にならない。入力→期待する結果の組を書く。
5. **証拠の形が決まっている**。何を PR に貼れば合格が示せるか（コマンドと出力、スクリーンショットなど）を書く。

### 2-2. テストと画面の使い分け
| 種類 | 使う場面 | 確認の中身 | PR に貼る証拠 |
| --- | --- | --- | --- |
| テスト | 関数・API・DB など、入力と出力で決まるもの | コマンド（例: `pytest …`）を実行する | 実行したコマンドと、出力の最後の行（例: `3 passed`）。CI があれば CI ログの URL |
| 画面 | 見た目・操作・画面遷移・表示文言 | 手順どおり操作して、画面の状態を見る | 操作後の画面のスクリーンショット（手順の最後の状態が分かるもの） |

1つの作業に両方が要るときは、行を分けて両方書く（例: 検証関数はテスト行、エラー表示は画面行）。画面だけで済ませられるものをテストにしたり、テストで足りるものに画面確認を足したりしない。

### 2-3. 悪い例 → 良い例
以下の例はこの規定のための仮の題材で、実際のプロジェクトの仕様ではない。

**テスト型**

| 悪い例 | なぜ判定できないか |
| --- | --- |
| 全関数を実装する | 「全」の範囲も、できた状態も決まっていない。何をしたら合格か分からない |

良い例（表の1行として）:

| # | 確認の種類 | 確認手順またはコマンド | 合格の基準 | 証拠の形 |
| --- | --- | --- | --- | --- |
| 1 | テスト | `pytest tests/test_membership.py -q` | 全件通る。状態が「申込済み」なら `is_active()` が `True`、「キャンセル済み」なら `False` | コマンドと出力の最後の行（例: `4 passed`）を PR に貼る |

**画面型**

| 悪い例 | なぜ判定できないか |
| --- | --- |
| 申込画面が正しく動く | 「正しく」の基準も、どの操作を見るかも決まっていない |

良い例（表の1行として）:

| # | 確認の種類 | 確認手順またはコマンド | 合格の基準 | 証拠の形 |
| --- | --- | --- | --- | --- |
| 2 | 画面 | `streamlit run app/frontend/app.py` で「申込」を開き、氏名を空のまま「送信」を押す | 「氏名を入力してください」が赤字で出る。登録済み一覧の件数が増えない | 送信後の画面のスクリーンショットを PR に貼る |

### 2-4. 書いたあとの自己確認
- 各行を読んで「私以外の人が、この行だけで ○/× を付けられるか」を考える。付けられなければ書き直す。
- 完了条件が書けない Issue は、まだ起票しない。書けない理由は、仕様が決まっていないことが多いので PM に確認する。

## 3. Issue の大きさの目安（案）
- 1 Issue = 1 PR。1 つの PR で閉じられる大きさにする。
- 目安: 1〜2 日で終わる。完了条件が 3〜7 行。触るファイルが 5 つ前後まで。
- 完了条件が 8 行を超える・触るファイルが 10 を超える・テストと画面が大量に混ざる場合は、分けられないか考える。分ける時は、元の Issue を残して、子の Issue を「依存」でつなぐ。
- 逆に、1 行の変更だけの Issue がいくつも続く場合は、まとめられないか考える。

## 4. 仕様変更で増えたタスクの起票ルール（案）
5文書が変わったり、実装中に新しい作業が見つかったりしたときの起票のルール。

| いつ | 誰が起票する | 起票前に必要なこと |
| --- | --- | --- |
| 5文書の変更が承認され、実装の作業が増えた | 5文書を変えた PR を出した人 | PM の承認（変更の PR のマージ）。Issue の「対応する文書の ID」と「依存」に、その変更の ID と PR を書く |
| 既存 Issue の実装中に、別の作業が必要と分かった（範囲外の作業） | 見つけた人 | Issue は起票してよいが、着手は PM に確認してから。元の Issue の「やらないこと」にその Issue の番号を書く |
| レビューで「文書と実装の食い違い」を指摘された | 指摘した人、または担当者 | 直す先が文書か実装かを PM が決めてから。文書を直すなら上の1行目の扱い |
| 既存 Issue の完了条件を変えたい | 担当者が PM に依頼する | PM の承認。承認の記録（コメント）を Issue に残し、PM が完了条件を更新する（担当者が勝手に直さない） |

- 起票するときも、§2 の完了条件を書く。書けない場合は起票しない（§2-4）。
- 起票した Issue が既存の Issue と重複しないか、先に一覧で検索する。

## 5. 任せてよい範囲の書き方
Issue ごとに「自分で決めてよいこと」と「PM に確認が要ること」を分けて書く。裁量欄を空にしない。

- 自分で決めてよいこと（例）: 関数名・変数名、エラーメッセージの細かい言い回し、テストデータの値、ファイル内の整理
- PM に確認が要ること（例）: 画面の項目の追加・削除、API の入出力の変更、新しいライブラリや外部サービスの追加、完了条件の変更、スコープの増減（`00_ルール/PRレビュー規定.md` §3-3 と同じ）
- 決めた内容は PR 本文に一言書く。

## 6. AI レビューとの関係
AI レビュー（`scripts/scheduled/review-routine-prompt.md`）は、Issue の完了条件の表を1行ずつ判定する。判定できない書き方の完了条件（§2-1 を満たさないもの）は、承認せず、Issue の直しを求めるコメントが付く。
