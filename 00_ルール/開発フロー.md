# 開発フロー（5文書の作り方・段0〜7）

案件の進め方の正本。上から順に使う。いつでも守る基本（承認・秘匿情報・Git・役割）は [[作業ルール]]。
2026-10-29 本人承認。旧「V字フロー規定」をここに統合した（実際の案件の振り返りと、Anthropic が公開している Claude Code の使い方を合わせて作成）。

## 1. 全体図

```
要求 ──▶ 要件 ──▶ 仕様 ──▶ 設計 ──▶ 実装
  ▲         ▲         ▲         ▲        │
  │         │         │         └─ 単体 U ┘
  │         │         └───────── 結合 I
  │         └─────────────────── システム S
  └───────────────────────────── 受入 A（自己評価 → 見直し）
```

左の文書を、同じ高さの右のテストで確かめる（V字）。文書は §3 の段0〜6で作り、段7で作って右側を下から確かめる。

## 2. どの段でも回す「問いと回答」の輪

文書は一度に書き上げない。段0から段6まで、毎段この輪を回して育てる。

```
りじちょーが文書案と問いを出す（一問ずつ・案付き）
  → 本人が答える（「Aで」「決定」）
  → 文書を更新し、本人の言葉を記録
  → 未決が残っていれば最初に戻る
```

**次の段に進む条件**: 未決が0。決められないものは「保留」にし、確認する人・期限・確認事項・決め方を書く。保留に依存しない作業は進めてよい。

りじちょーの作法:
- 抜けている項目を質問で埋める。一問ずつ、聞く理由を短く添える
- 選択肢は提案してよい。「A（〜）と B（〜）があります。わたしは A を勧めますが、決めてください」
- 決めるのは本人の明示（「Aで」「決定」）。「任せる」でも1つに絞って「これで決定しますか」と聞く。「どっちも」「たぶん」は決定にせず聞き直す
- 個人回答の原文は上書きしない。AI が全欄を代筆した回答は本人の証拠にならない
- 文書が甘いところ（測れない受入基準、主語が無い、エラー・境界が無い、文書どうしの食い違い、未決を断定で書いている）は、「どの行が・なぜ・どう書けば測れるか」で指摘する。直すのは本人
- 変えたことは、図・モックに「変更」の札と前の書き方（取り消し線）と ID を付けて残す

## 3. 段ごとの中身

| 段 | 見せるもの | りじちょーの問いの例 | 人が決めること | 残す記録（文書と ID） | 対応するテスト |
| --- | --- | --- | --- | --- | --- |
| 0 企画書と課題 | `inputs/` の企画書・仕様書と個人回答。資料が無ければ、りじちょーが会話から企画書を書いて `inputs/` に置く。そこから起こした、今のやり方の流れ図と、かかる時間 | 「この企画書で、一番困っている人は誰ですか？」「今の作業で、一番時間がかかっているのはどこですか？」 | 中心の問い（案件ごと）、決める人（PM）と参加者、企画書の中身が合っているか、何を減らすか、誰のためか、成功の定義 | `inputs/` の原本、個人回答.md、要求.md（R、受入基準） | 受入 A |
| 1 要件の骨組み | 機能の一覧と、§5 の非機能の見出し | 「何秒以内なら待てますか？」「間違えて送ったら、どう戻しますか？」「本物を使わずに試せる環境はありますか？」 | 基準の数字（仮でよい）、要件1行ごとの受入基準、確かめるまで分からない要件への「未検証」の印 | 要件.md（F/N） | システム S |
| 2 前提の小さな試し | 「未検証」の印が付いた前提だけを、本物で1回ずつ試した結果。**本番には書き込まず、読むだけ**。印が0件なら飛ばす | 「この一覧は取れませんでした。代わりに A と B、どちらにしますか？」 | できないときの代わり | 試しの記録（G）、要件の直し（印を外す） | — |
| 3 動きの確認 | 担当別の流れ図（人・ツール・AI・外部サービス）、画面遷移図 | 「ここで人が確かめる必要はありますか？」 | 人の手が要るところ、外と話すところ | 仕様.md（SP、決定の行 M） | 結合 I |
| 4 触れるモック | 架空の値で押せる画面。決める人と使う人が1件ずつ通して操作する | 「送るまでに押す回数は何回まで許せますか？」 | 画面の形、押す回数、知らせの出し方 | 仕様.md、モックの原本 | 結合 I |
| 5 仕様・設計を固める | 状態遷移図、データの表、安全の受け持ち、速さの実現方法 | 「結果が分からないとき、自動で送り直しますか？」 | 残った未決の決着 | 仕様.md（SP）、設計.md（D、AI が書き人がレビュー） | 単体 U |
| 6 テストを先に書く | 試験の一覧と試験そのもの（先にコミット）、実装計画、承認する版 | 「この版（コミット）で作り始めてよいですか？」 | 「OK、進めて」（[[作業ルール]] の版付き承認） | テスト設計.md（トレーサビリティ表）、試験のコミット、IMPLEMENTATION_PLAN.md | A/S/I/U を設計 |
| 7 段ごとに作る | 試験の件数、**モックと実物の画面の見比べ**、1件の旅の学習ページ、**段ごとに**本番で1件だけの確認 | 「本番の1件は想定どおりでしたか？直すところは？」 | 合格か、直すか | 本番確認の記録、振り返り（次の段の仕様へ戻す） | U → I → S を実行 |

- 段7の作業は Issue に切って進める（書き方は [[Issue作成規定]]）
- 実装中に新しい決めごとが出たら、段3か段4に戻って輪を回してから決める
- 段7のテストは段6でコミットしたものを使う。作る人はテストを変えない。変えたいときは仕様の変更として段5に戻る
- 段7の単体・結合・システムが通ったら、初回提出版をコミット ID で固定する
- **りじちょーの最後の確認（段7、コミット前）**: 報告とテスト結果だけでなく差分を読み、各変更が仕様のどの ID に当たるかを確かめる。ID の無い変更は止めて本人に見せる。通常の道の大きな変更だけ、`/code-review` を一番軽い設定（low）で1回走らせる。小さな直しの道では使わない

## 4. 5文書の完成の条件

| 文書 | 答える問い | ID | 完成の条件 |
| --- | --- | --- | --- |
| 個人回答.md | 本人が AI と話す前に、誰が・何に困り・どうなれば嬉しいか | — | 原文が上書きされていない。対話後の変更と理由がある |
| 要求.md | 誰が、何のために、何ができると嬉しいか | R、受入基準 | 使う人・困りごと・成功の定義が書かれ、「困っていること」と「できると嬉しいこと」が食い違わない。未決が無い |
| 要件.md | 何を満たせば要求に応えたことになるか | F／N | 各要件に ID と測れる受入基準がある。§5 の必須の見出しが空欄でない |
| 仕様.md | 具体的にどう振る舞うか | SP（決定の行は M） | 入力・出力・画面・データ・エラー時の挙動が要件 ID と紐づく。主要導線は「画面の状態 → API → データ → 期待結果」の1行 |
| 設計.md | どう作るか | D | 構成・データ・処理の流れが、仕様の見出しか要件 ID に紐づく |
| テスト設計.md | どう確かめるか | A／S／I／U | 要件 ID ごとにテスト（前提・操作・期待結果）がある。末尾のトレーサビリティ表で 要求 → 要件 → 仕様 → 設計 → テスト がつながる |

テストの受け持ち:

| テスト | 誰が設計 | 誰が実行・判定 |
| --- | --- | --- |
| 受入 A | りじちょーが補佐 | 本人（自己評価が先、見直しが後） |
| システム S | りじちょー・Kurosu | Kurosu |
| 結合 I | Takahiro | Kurosu |
| 単体 U | Terao / Mi-rin | 実装担当 |

記録の決まり:
- 本人の決定は `ADR.md` に1行ずつ（起点・何を・なぜ・捨てた案・撤退ラインの仮説）。各文書の「決定事項」は ADR の ID だけ書く。全項目に ADR を求めない（実装・評価・安全に影響する判断に絞る）
- `.docx` の資料は pandoc で md に変換してから読む。以降は md が正本。資料に書いてあるだけでは決定としない
- 各段の通過は自己点検で ○△× を付け、証拠のパス（テスト結果・ログ・スクリーンショット）を `evidence/` に残す。「できたと思う」は △

## 5. 要件の非機能の見出し（段1）

- **必須の5つ（空欄で進めない）**: 速さ・安全・費用・戻し方・試験のしかた
- **関係するかを一問ずつ確かめる5つ**: 環境・使いやすさ・法令（会社の決まり）・保守・共有への備え。関係するものだけ見出しを立てる
- 対象外は要件の雛形の「対象外・保留・ADR」の節に書く

## 6. 図とモックの置き場

- **原本はリポジトリ**: 流れ図・画面遷移図・状態遷移図は `.md` の Mermaid（文字で書く図）で書く。触れるモックは HTML で `02_プロジェクト/<案件>/evidence/mock/` に置き、コミットする
- **見せるのは Artifact**（claude.ai の非公開ページ）: 見せたい人にだけ共有する。図とモックは「生きている1枚」にし、同じ URL のまま出し直して版を重ねる
- 値は架空だけ。本物の ID・番号・氏名・金額・秘匿値を入れない
- GitHub Pages など外部公開は、運営の承認がある案件だけ（`CLAUDE.md`「セキュリティ」）

## 7. 変更の大きさで道を分ける

| 道 | 当てはまるもの | 進め方 |
| --- | --- | --- |
| 通常の道 | 新しい機能、新しい画面、新しい外部とのやり取り、データの形の変更 | 段0〜7を通し、段6で版付き承認 |
| 小さな直しの道 | 上に当てはまらない直し（文言、並び、既定値、知らせの出し方など） | 仕様の行1つ（本人の回答と日付を引用）＋試験＋図・モックの更新。仕様の行の本人回答を承認とみなす（[[作業ルール]] §1） |

迷ったら通常の道にする。どちらの道かは、りじちょーが案を出し、本人が決める。

## 8. 未決のまま進める場合

- 本人が「未決のまま進めて」と明示したときだけ、実装計画に進む。その旨と未決の項目を計画に書く
- スタッフと Claude Code は、未決の部分を補わず、その部分を作らずに「仕様に書かれていません」と報告して止まる。りじちょーは止まった箇所を本人に見せ、埋めてから続ける（文書の穴がそのまま実装の穴になることを体験するため）

## 9. 評価（W4）と振り返り

- **自己評価が先**: 自分たちの要求・受入基準に照らして、本番で「できた／想定と違った」と良い点・課題を `evidence/self-review.md` に書く
- **見直しが後**: 時間を置くか、別観点（AI スタッフの相互レビュー、指摘 ID `X-連番`）で読み直し、「気づいていなかった点」を足す
- 結果を見て評価基準を変えない。変えるなら理由と影響を ADR に書き、本人の再承認を受ける
- 案件の終わりに Keep / Problem / Try を3行ずつ。Try は次の案件の文書とこのファイルに反映する

## 10. 忘れないための関門

| 関門 | 中身 |
| --- | --- |
| 段の出口 | りじちょーが「未決0・図とモックが最新」を確かめてから次の段に進む（`.claude/agents/rijicho.md`） |
| コミット前 | `仕様.md` の仕様の行（M/SP）を足すか直したのに `evidence/mock/` が同じコミットで変わっていなければ、pre-commit が警告する（止めはしない。更新が要らなければそのまま進めてよい） |
| PR の CI | PR の CI（`.github/workflows/`）が落ちたらマージしない。テストを足したら、CI で走らせる工程も同じ PR に足す（`--no-verify` は [[作業ルール]] §6-2 で禁止） |
| PR | 「図とモックを更新した／変更なし」「テストを変えていない」のチェック欄（`.github/pull_request_template.md`）。レビューのしかたは [[PRレビュー規定]] |

リポジトリを複製したら、最初に1回 `git config core.hooksPath .githooks` を実行する（しないとコミット前の関門が動かない）。

## 11. 用語

| 用語 | 意味 |
| --- | --- |
| 二入口 | 会話から始める（りじちょーの一問に答えて文書案を育てる）と、資料から始める（`inputs/` の資料をりじちょーが先に読む）の2つ。どちらも最初に企画書を `inputs/` に置いて開始点をそろえる |
| 個人／チーム | 個人回答（本人が対話前に書く）と、チームでの採用・統合・保留・不採用の区別。決める人（PM）を実装計画に書く |
| 判断ポイント | 実装・評価・安全に影響する判断（目的・基準・確認した事実・採用案・他案の扱い・見直す条件）。ADR に残す |
| 保留 | 決められない論点。確認する人・期限・確認事項・決め方を書く |
| 版付き承認 | 5文書のコミット ID（対象版）を実装計画に書き、PM が「OK、進めて」と明示した記録。版が変わったら古い承認は使わない（[[作業ルール]] §1） |
| 節の採用・確定 | りじちょーの案を読み、本人が「Aで」「決定」と明示して文書に取り込むこと |

munder を使わないチームも、同じことを Markdown の5文書と Claude Code、PR で行う。
