# 作業ルール

チーム全員（りじちょー・スタッフ・Claude Code・参加者）がいつも守る基本の規定。最初にこれを読み、案件の進め方は `00_ルール/開発フロー.md` を上から順に使う。

## 1. 計画 → 承認 → 実装
1. 計画: 何を・なぜ・どう作るかを示す（実装計画に対象版・担当・根拠 ID・完了証拠）。
2. 承認（版付き承認）: 5文書のコミット ID を示し、ユーザーが「OK、進めて」と明示するのを待つ。承認前に作り始めない。版が変わったら古い承認は使わない。
3. 実装: 承認後に作る。

例外: 小さな直し（文言・並び・既定値など。新しい機能・画面・外部とのやり取り・データの形の変更を含まないもの）は、仕様の行に引用した本人の回答を承認とみなす（`開発フロー.md` §7）。

## 2. 既存資産を先に読む
いきなり作らず、案件フォルダの 5 文書・`inputs/`・`01_ナレッジ/index.md` を先に読む（`voice/` があればそれも）。

## 3. 日本語・具体
回答・コメント・文書は日本語。コマンドはコピペで動く形で示す。Mac と Windows で違う場合は両方書く。

## 4. 作業範囲
作業対象はこのフォルダ配下。外のファイルを読む・書くときは、対象を示して承認を得る。

## 5. 完了報告は証拠つき
テスト結果・実行ログ・生成物のパス・本番 URL を添える。証拠なき完了報告は受け取らない。

## 6. 秘匿情報
`.env`・API キー・パスワードはコミットしない。ナレッジや文書にも書かない。`.env` は読まない・書かない・値を聞かない（変数名は `env.example` を見る）。OpenAI のキーは API 側の環境変数だけ。

## 6-2. 事故防止（Git）
- `main` に直接コミット・push しない。作業ブランチを切って PR にする
- `git push --force`・`git reset --hard`・`git clean`・`rm -rf`・`--no-verify` を使わない・提案しない
- TA（支援者）はコードを直接修正しない。PR コメントと回答まで

## 7. 役割の境界
- りじちょー: 壁打ち・計画・割り振り・最終確認。**決断はしない**（ユーザーが決める）。実装もしない。
- スタッフ: 割り振られた範囲だけを、文書どおりに作る。範囲外・未記載は止まって報告する（未決のまま進めても、未決の部分は作らない）。
- 書記: 学びと決定の記録。index / log の更新。
- 参加者: 個人回答の原文は本人が書く。採否・承認・受入は人が行う。

## 8. AI スタッフの心構え
- 中心の問いの意図を全工程で共有する。参加者の仮説・要求は、証拠と理由を残して変えてよい。教材から新しい機能の正解を示さない
- 本人の原文を上書きしない。事実と仮説を分ける質問、選択肢と影響の比較、文書間の ID の追跡、未決の発見を支援する。採否・承認・受入は代行しない
- 未決の部分は補わず、作らずに「仕様に書かれていません」と報告して止まる（`開発フロー.md` §8）
- 生成AIを使います。揃えた条件・残る差・逸脱は記録します
- 作る人は、段6でコミットしたテストを変えない（`開発フロー.md` §3）
