# 11/24 発表中の共有リンク停止：原因の調査と対策案（Terao・2026-11-25）

PM の決定（11/25「原因を調べて案にする」）にもとづく調査です。コードは変えていません。本番（App Service・Functions）には何も当てていません。

## 1. 結論

画面側のサーバーが、1 台（B1・1 vCPU）で、共有ページの 1 訪問ごとに多くの CPU を使う作りになっています。人が一度に集まると CPU が足りなくなり、応答が待ち行列に積もったと見ています。

訪問 1 回の CPU の大半は、共有ページの HTML の描画ではありません。`next start` が、JS・CSS を毎回 gzip で圧縮している分です。手元の測定では、訪問 1 回あたり 39ms の CPU のうち、圧縮を止めると 10.5ms に下がりました。

ただし、Azure 上の CPU・メモリの実測は私は見ていません。「原因」は手元の再現とコードからの見立てです。確定には、PM が 11/24 の発表時間帯の App Service プランの指標（CPU・メモリ・Http 5xx・応答時間）を見る必要があります（§6）。

## 2. 共有ページを開いたとき、画面側のサーバーで走るもの（コードの根拠）

- **共有ページの HTML は、毎回サーバーで作られます。** `frontend/src/app/s/[share_id]/page.tsx` は `params` を `await` して `<SharedView>` を返します。ビルド結果は `ƒ /s/[share_id]`（動的）で、応答ヘッダーは `Cache-Control: private, no-cache, no-store`、つまり使い回されません。トップ `/` と `/search` は `○`（静的）で `s-maxage=31536000` です。
- **描画の中身は軽いです。** データは取りません。`SharedView` は `"use client"` で、中身はブラウザが `fetchShared`（`frontend/src/lib/sharedLink.ts`）で API から読みます。HTML は 13.5KB です。
- **画像の最適化は動いていません。** 全部の `<Image>` に `unoptimized` が付いています（`SharedView.tsx:151` ほか）。`/_next/image`（CPU を食う sharp）は使われません。
- **ミドルウェア（`middleware.ts`・`proxy.ts`）はありません。** `next.config.ts` は、全応答に `X-Robots-Tag` を付けるだけです。`rewrites` は開発時（`development`）だけです。`compress` は未指定なので、既定の `true`（gzip）です。
- **JS・CSS・画像はすべて Node が配ります。** 共有ページ 1 訪問で、HTML 1 本と、JS 9 本・CSS 2 本・画像 3 本の、計 15 リクエストが同じ Node に来ます。`.github/workflows/main_gen13-app-step3-1-5181-fe.yml` を見ると、デプロイは `.next` ごと zip で送るだけで、CDN などは前にありません。
- **JS・CSS は、リクエストのたびに gzip されます。** `next start` の圧縮は事前計算ではなく、毎回です。最大の JS は 229KB で、gzip で 72KB になり、1 リクエストで約 9.5ms の CPU を使いました。
- **起動は速いです。** `next start` は 1.1 秒で最初の 200 を返しました（手元）。Always On が切れていても、起動の遅さは主因になりにくいです。

## 3. 手元の測定

条件：MacBook（8 コア・Node v24.20.0）、`next build` → `next start`、ポート 3200〜3203（3100・3101・8000 は触っていません）。API は使いません（画面側の送信だけ。ビルドの `NEXT_PUBLIC_API_BASE` はダミーの `http://127.0.0.1:3999`）。負荷は同じ PC の `load.mjs`（このフォルダ）です。

**ここの数字は絶対値ではありません。** 手元の PC は B1（1 vCPU）より速く、負荷をかける側も同じ PC にいます。比べるのは、版どうしの相対です。

## 4. 止まった原因の見立て

1. **（主）CPU が足りなくなりました。** 共有ページ 1 訪問で、手元で約 39ms の CPU を使います。B1 の 1 vCPU は手元より遅いはずで、仮に 3 倍遅いとすると約 120ms/訪問です。このとき、1 秒に 8 人が処理の限度になります。発表中に数十〜数百人が数秒のうちに開くと、待ち行列が秒単位で積もります（手元でも、同時 500 人で最大 25 秒）。この 3 倍は仮定です。
2. **（副）メモリが増えます。** 同時 1000 人で、手元でも 860MB まで増えました。B1 の RAM は約 1.75GB なので、余裕は大きくありません。
3. **（副）Health Check がありません。** 応答しなくなっても、Azure が検知して入れ替えることがありません。60 秒の無応答と 503 は、この組み合わせに合います。
4. **API は関係ありません。** API は 50 件同時で、すべて 200・0.7 秒以内でした。ブラウザは HTML を受け取ったあとで API を呼ぶので、止まったのは、その前の画面側です。

「共有ページの HTML を毎回描画していること」自体は、主因ではありません。静的にしただけでは、訪問あたりの CPU は 39 → 36.5ms しか下がりませんでした。社長の言う「毎回クエリを発行しない」に近い、DB や API を毎回引く処理は、そもそも画面側にありません。

## 5. 対策の案

「効き目」は、手元の訪問あたり CPU（いまのまま 39ms）に対する値です。Azure での効き目は、PM の確認（§6）が済むまで見込みです。

| # | 案 | 手間 | 費用 | 効き目 | 運営への相談 |
| --- | --- | --- | --- | --- | --- |
| A | `next.config.ts` に `compress: false` を足す | 1 行。画面側のコードの直し（別 PR・別 Issue） | 0 円 | CPU が約 1/4（39 → 10.5ms）。代わりに送るバイト数は増える（最大の JS で 72KB → 229KB） | 不要（コードだけ） |
| B | 共有ページの枠を静的にする（`generateStaticParams` + `dynamicParams`） | 数行。別 PR | 0 円 | HTML は 1 回描いて使い回す。単独では訪問あたり 39 → 36.5ms。A と合わせると 6ms（約 1/6.5） | 不要 |
| C | Health Check を有効にする（パスは `/` など静的ページ） | Azure の画面の設定（PM の手作業） | 0 円 | 応答しなくなった台を、Azure が検知して入れ替える。止まる前に防ぐものではない | 設定変更なので PM の確認。運営への相談は不要と思うが、判断は PM に任せる |
| D | Always On を有効にする | Azure の画面の設定（B1 は設定可能） | 0 円（B1 は追加費用なし） | 一定時間アクセスが無い後の、起動待ちを防ぐ。手元の起動は 1.1 秒なので、今回の主因には効かない見込み | 不要 |
| E | 台数を増やす（B1 → 2 台 など） | Azure の画面の設定 | B1 の台数に比例して増える | 処理の限度が台数に比例して増える。A・B で足りるなら不要 | **必要**（料金が増える） |
| F | 前に CDN（Azure Front Door・CDN）を置き、静的ファイルを配る | 構成の変更が大きい | 月額の費用あり | 静的ファイル（15 リクエストのうち 14）が App Service に来なくなる。最も効くが、外部サービスの追加 | **必要**（外部サービスの追加と費用） |
| G | 共有ページの「読み込み中」の枠だけを、静的ホスティング（Azure Static Web Apps など）に移す | 大きい | 要確認 | 画面側のサーバーを通らない | **必要**（外部サービス）。今回の規模には大きすぎると見ている |

### おすすめ

**A + B を先に、C と D を同時に設定するのがよいと思います。**

- A + B はコードを数行足すだけで、費用が 0 円です。手元では訪問あたりの CPU が約 1/6.5、HTML だけなら同時 1000 人で p95 が 6.0 秒から 1.4 秒になりました。
- C は、止まったときに自動で戻る保険です。D は無料で、副作用が見当たりません。この 2 つは PM の手作業です。
- E は、A・B を入れて再測定してから、足りなければ運営に相談する順がよいと思います。
- F は効きますが、外部サービスの追加なので、今回の規模（人数が数十〜数百人の発表）には、先に A・B で足りるか確かめたいです。

**A の注意：** `compress: false` で送るバイト数が約 3 倍になります。App Service の前段が代わりに圧縮するかは、私は確認できていません（Azure は見ていません）。転送量と表示の速さへの影響は、公開後に PM が確認してください。

## 7. 限界

- 負荷をかけた PC と受ける PC が同じで、B1 とは CPU 性能が違います。絶対値（秒あたり何人）は Azure に当てはめられません。版どうしの相対と、どこが重いかだけが根拠です。
- 同時接続の失敗 86 件（`compress: false` のみ・同時 1000 人・1 回）は、手元のクライアント側の接続エラーとみられますが、原因は調べていません。他の同時 1000 人の測定（2 回）では 0 件でした。
- 「B1 は手元より 3 倍遅い」は仮定です。測っていません。
